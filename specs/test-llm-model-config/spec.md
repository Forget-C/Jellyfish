# Feature Specification: 模型配置验证（模型管理）

**Workspace**: `test-llm-model-config`  
**Created**: 2026-05-06  
**Status**: Ready for planning  
**Input**: 用户描述: "帮我给模型管理里面，配置的模型新增一个测试的功能，方便验证模型是否配置正确"

---

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 对已保存模型发起一次配置验证 (Priority: P1)

作为 **负责接入与维护模型配置的人员**，我希望 **在「模型管理」中对某条已保存的模型发起一次配置验证**，以便 **在正式用于剧本/分镜/生成等业务流程之前，确认该模型在当前供应商与参数下可被正确调用**。

**Why this priority**: 这是需求的核心价值：把「配了但不知道能不能用」变成「可快速得到明确结论」，直接减少后续排障成本。

**Acceptance Scenarios**:

1. **Given** 模型管理列表中已存在至少一条已保存的模型记录（已绑定供应商且已保存）  
   **When** 用户在列表行的操作区选择「测试生成」或等价的「配置验证」入口  
   **Then** 系统针对该模型的类别与绑定关系执行一次验证，并在界面上给出 **明确的成功或失败结论**，失败时给出 **可用于排错的中文说明**（不涉及完整密钥等敏感信息的展示）。

2. **Given** 用户已通过列表打开某模型的详情视图，或使用卡片视图浏览模型  
   **When** 用户在详情或卡片上的等价入口发起「快速测试 / 配置验证」  
   **Then** 行为与列表入口 **一致**（同一套验证语义与结果展示原则）。

3. **Given** 用户刚修改并保存了某模型的供应商、模型标识或参数  
   **When** 用户立即对该模型发起配置验证  
   **Then** 验证应基于 **最新已保存的配置** 执行，使用户能确认保存结果是否生效。

4. **Given** 验证结果为成功，且当前用户具备模型或系统管理权限  
   **When** 用户展开「详情」  
   **Then** 可见 **已脱敏** 的扩展信息；**Given** 当前用户不具备相应权限 **When** 查看同一结果 **Then** **不得** 展开或不得看到详情中的扩展信息（与 FR-006 一致）。

**Edge Cases**:

- **边界条件**：模型已保存但关联的供应商已被删除或不可用——验证应失败，并提示用户先恢复或调整供应商配置。
- **边界条件**：模型类别与供应商对该类别的支持关系不一致（历史数据或误配）——验证应失败或明确警告，并提示检查类别与供应商的匹配关系。  
- **错误场景**：上游服务超时、限流、鉴权失败、模型不存在——失败信息应区分「网络/服务不可用」「鉴权失败」「模型或参数不被接受」等大类，避免笼统的「失败」。
- **错误场景 / 并发场景**：验证进行中若用户 **重复点击**，系统 **不并行发起第二次验证**（以首次为准或对后续点击给出明确忽略/禁用提示）。若用户 **离开当前模型管理上下文**（例如切换路由、关闭承载验证的界面），视为 **用户取消本次验证的等待**；不要求界面在离开后仍必须展示最终结果（已知可能产生已发起但未展示的上游调用，本期接受该权衡）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须在「模型管理」中，对 **单条已保存模型** 提供 **显式的配置验证入口**（与当前界面上的「测试生成 / 快速测试」意图一致），且入口在 **列表行、卡片视图、详情视图** 中 **至少覆盖列表行**；若其他位置已展示按钮，则须 **同为可用入口或明确移除/禁用并说明原因**。
- **FR-002**: 配置验证必须 **按模型类别**（文本生成、图像生成、视频生成）采用 **与该类别相符的验证含义**，且至少能区分「配置根本不可用」与「配置可用」。其中 **图像/视频类** 的「通过」以 **鉴权、连通与接口级能力探测** 为准，**不要求** 完成真实最小成片/成图；本期接受其可能无法覆盖「接口可用但生成链路异常」的边角风险，以换取更低成本与更短反馈时间。
- **FR-003**: 验证过程中，用户必须能感知 **进行中状态**（例如加载中、防重复误触的提示）；验证结束后必须展示 **最终结果**（成功/失败）。
- **FR-004**: 验证失败时，系统必须提供 **可操作的排错提示**（例如建议检查供应商密钥、模型名称、参数 JSON、网络环境），且 **不得** 在界面展示完整的 API 密钥或其它应保密的凭据内容。
- **FR-005**: **不强制** 要求用户先完成供应商侧的「连接/健康」测试才能发起模型验证；若系统已提供供应商测试，可作为 **可选排错路径** 向用户提示。模型级验证仍应尽可能暴露 **「供应商通道可用但模型标识或参数不被接受」** 等与模型配置直接相关的问题。验证进行中 **重复触发** 不得并行发起多次相同验证；用户 **离开当前模型管理上下文** 时的取消语义见 User Story 1 的 Edge Cases。
- **FR-006**: 验证 **成功** 时：默认展示 **验证通过**（可展示耗时等轻量信息）。同时提供 **可展开的「详情」** 入口；**详情内容仅对具备模型或系统管理权限的用户可见**（与产品现有权限划分对齐，不在本 spec 规定技术实现），且须 **脱敏**（不得展示完整密钥或等效敏感凭据）。详情用于增强排错与可信度，**不得** 默认向无权限用户展开。

### Non-Functional Requirements *(if applicable)*

- **NFR-001**: 验证调用应具备 **合理超时**，避免界面长时间无反馈；超时应有明确失败提示。
- **NFR-002**: 验证行为应遵守现有权限与租户/项目隔离约定（若模型管理已受登录与权限约束，则验证不得绕过该约束）。
- **NFR-003**: 「详情」中的扩展信息默认折叠；其可见性必须符合 **FR-006** 的权限与脱敏要求。

### Key Entities *(if applicable)*

- **模型（Model）**: 用户配置的、绑定某一供应商的一条模型记录，含类别、参数、描述等；验证对象。
- **供应商（Provider）**: 提供调用通道与凭据的配置实体；模型验证通常依赖其可用性，但模型级问题应能单独暴露。

## Out of Scope *(if applicable)*

- 一次性对 **全部模型** 做批量验证或巡检报告（可作为后续增强）。
- 将每次验证自动记录为 **正式异步生产任务** 并在任务中心展示完整业务上下文（除非后续产品明确要求；本期以「配置侧快速验证」为主）。
- 在验证流程中编辑模型字段（验证与编辑分离；用户可先保存再验证）。

## Resolved Decisions *(2026-05-06)*

以下结论来自需求方在规格澄清中的选择，已反映于 FR-002、FR-005、FR-006 及 Edge Cases：

| 主题 | 选择 | 摘要 |
|------|------|------|
| 图像/视频验证深度 | **B** | 以鉴权/连通/能力探测为主，不要求真实最小成片/成图 |
| 成功反馈 | **C** | 默认「通过」+ 可展开「详情」；详情仅对有管理权限的用户可见且须脱敏 |
| 供应商测试与交互 | **A** | 不强制先测供应商；重复点击不并行；离开上下文视为取消等待 |
| 文本生成类（补充） | **未单独表决** | 仍须满足 FR-002：能区分「根本不可用」与「基本可用」；成功展示遵循 FR-006 |

## Context from Exploration *(for planning)*

- 「模型管理」中已有与「测试」相关的界面元素，但 **模型级验证尚未对用户生效**；「供应商管理」侧已有 **连接类测试** 的相邻能力。
- 「模型」在后端侧当前体现为 **可维护的配置数据**；**模型级验证** 在规格上视为 **新增业务能力**（本 spec 不规定实现方式）。
