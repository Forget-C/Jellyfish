Jellyfish · Internal Project

Setup & Test Complete

Standing up this Jellyfish instance and validating whether its script → shot → keyframe → video pipeline could reliably produce a coherent short episode, before committing time or budget to a real content pilot.

What happened

1. Feasibility test. Stood up a local instance and ran a deliberately-written test script through the real pipeline, producing a real 6-shot, ~48-second test episode — script broken into shots by an LLM, two reusable character keyframes, six image-conditioned video clips, stitched together. This proved episodes can be made on purpose, not by accident (the alternative — ad hoc use of consumer tools like Google Flow — took ~20 minutes of trial and error for one clip in initial exploration).

2. xAI (Grok) provider adapter. Wrote and merged a native provider adapter (text, image, video) following the repo's existing OpenAI/Volcengine pattern.

3. Switched to Gemini (Veo). After live comparison, replaced the xAI adapter entirely — better fit for a dialogue-driven drama format, comparable cost, no code left behind for a provider no longer in use.

Why Gemini over xAI

xAI (Grok)Gemini (Veo 3.1)
Video cost (8s clip)~$0.40–0.65Lite: ~$0.40 · Fast: ~$0.80 · Standard: ~$3.20
Character consistencyWorks wellWorks well
Native spoken dialogueNoYes — matched to script
ReliabilityConsistent~2 of 5 attempts hit a safety filter

Native dialogue is the deciding factor for a drama format — it removes an entire production step (voiceover/lip-sync) the xAI pipeline didn't cover at all. Cost is a wash. The tradeoff is the safety filter's unpredictability, covered below.

Known issues

Unpredictable safety filter. Roughly 2 of 5 video generation attempts were rejected by a generic "audio" content filter on ordinary, non-explicit phrasing (a character "laughing," "raising hands defensively"). Calmer wording, and even explicit quoted dialogue, passed clean. Not charged when it fires, but budget time for retries when scripting real episodes.
Storage not exercised end-to-end. Local dev has no S3/RustFS configured — file persistence for generated media hasn't been verified past the download step in this environment. Should work with object storage configured in a real deployment.
