# 六部门专业输出契约

本文保留六岗工作单、审稿、审片与返工的专业语义。当前四画布的数据与执行边界见[场次架构](../architecture/directing-foundation.md)。旧 `SceneDesignRevision`、`PromptRevision` 和 `ReviewPacket` 表述属于仍可读取的固定版本契约，不表示当前画布需要逐层确认版本。

工作单、界面和执行文本使用同一份有来源的业务内容；模型输出不等于用户批准，生成成功不等于素材采用。声音设计不等于声音已生成；自动视频理解和自动会议提炼不由这些人工工作单能力推定为已实现。

## 4. 共用标识与六岗数据结构

### 4.1 共用标识

契约包含项目、章节、场次、镜头、资产、文件、生成单元、Take 和 Prompt 的稳定标识，另有设计快照内的 `beat_id`、`blocking_state_id`、`spatial_anchor_id`、`event_id` 和 `criterion_id`。初期可保存为结构化 JSON，不要求每项独立建表。

一个节拍可由多个镜头覆盖，一个镜头也可承载多个节拍。表演谱按 `beat_id + character_id` 组织，镜头通过覆盖关系选择适用行；镜头拆分重排不应强迫重写同一个人物行动。背景临时人物可以使用场次内稳定 participant_id，无需为了无名顾客建完整全局角色资产。

事实、创作建议、已确认决定和待核验信息使用明确标记。未填写、尚未知晓、不适用、明确为无是不同含义；不适用需说明原因。模型失败导致未输出不能被转成“本岗位通过”。每份工作单保留其依据版本及来源，人工确认事件由服务登记，不接受模型自称已获批准。

### 4.2 总导演：叙事与空间设计

`direction` 部分包含：

| 分组 | 业务内容 | 消费方 |
| --- | --- | --- |
| 本场目标 | 主要视点、信息变化、人物关系发展、关键转折、不可改事实 | 其他岗位、叙事审查 |
| 节拍序列 | 每拍事件、行动目标、阻碍、预期变化与必须让观众看到的内容 | 表演设计、镜头覆盖 |
| 调度状态 | 人物相对位置、朝向、主动权、动作路径及状态切换原因 | 摄影、连续性 |
| 空间依据 | 场所引用、稳定锚点、参考关系图、可拍摄区域、轴线、尺度判断和待核验点 | 参考选择、图片编译 |
| 覆盖与约束 | 各镜头叙事职责、必要反应/关系镜头、创作控制程度及验收标准 | 分镜和总导演审稿 |

这是对[导演语法](https://github.com/MasterLeos/leos-six-department-directing-team-skill-v1/blob/main/references/directing-grammar.md)的业务建模，不把可拍性判断替换为一段项目简介。首版可使用文字锚点和上传关系图，不强制开发三维场景编辑器。

### 4.3 表演指导：按节拍保留因果

`performance` 部分分为角色情境和节拍行。每行保留人物接收到的事件、行动目标与阻碍、潜在意图、注意对象、内部调整、可见身体行为、对白引用及表达方式、反应先后、离开该拍时的状态，以及应避免的表现和验收条件。

眼神、呼吸、身体重心、手部动作和声音可分别描述，但只填写当前动作真正需要的通道。不因界面有字段而要求模型全部生成。表演来源如果是用户视频或声音资料，应记录文件和时间范围；执行模型不支持对应输入时，显示能力缺口。

设计时的“在听完某句话后停顿”使用事件关系表达；只有已明确量化时才存延迟数值。实际素材中的秒数单独保存，不能把设计节拍直接当作视频时间码。依据见[表演指导](https://github.com/MasterLeos/leos-six-department-directing-team-skill-v1/blob/main/references/performance-direction.md)。

### 4.4 镜内执行：独立工作单

`staging` 部分按参与者/区域保存：景深层次、持续任务、路径、注意对象、触发事件、反应延迟、活动强度、入出画、对主叙事的作用及结束状态；另保存环境活动和刻意留白的理由。

作用是为分镜和编译提供明确的可见背景行为，并在审稿时核对是否遗漏参与者或出现无理由的同步反应。安静或无人场面允许明确为空，不自动添加群演。[岗位协议](https://github.com/MasterLeos/leos-six-department-directing-team-skill-v1/blob/main/references/role-council.md)

### 4.5 摄影指导：超出景别与运镜枚举

`cinematography` 按镜头保存以下分组：

- 叙事作用与可见结果，构图重心、空间层次和观察视点。
- 摄影机相对位置、高度及角度；焦段或等效空间效果、景深和焦点变化。
- 支撑/稳定方式、运动起点、触发、路径、速度和结束画面。
- 光源、人物经过的明暗区域、曝光与色温变化。
- 必要光学效果及出现条件，运动质感与已确认的技术参数。
- 与相邻镜头的衔接要求、禁止项与可观察验收条件。

具体焦段等数值可以未知，但意图和画面效果不能用空值掩盖。上述创作字段大多通过文本描述传给模型，并非声称供应商 API 都支持光圈或轨道参数。[摄影指导](https://github.com/MasterLeos/leos-six-department-directing-team-skill-v1/blob/main/references/cinematography-direction.md)

### 4.6 场记：状态、版本和实验分开

连续性计划使用 `continuity` 部分，按人物/物件/环境/摄影/声音分别记录前态、变化事件、后态与后续约束。人物空间、造型、手部和道具、环境、机位关系、对白/声音均有类型化分组；实际观察记录到 TakeReview 或 CutReview，不覆盖计划状态。[连续性协议](https://github.com/MasterLeos/leos-six-department-directing-team-skill-v1/blob/main/references/continuity-and-learning.md)

三本台账由已有业务记录组合，避免再建三套重复数据源：

| 台账 | 组成 | 保留的关联 |
| --- | --- | --- |
| 连续性账 | 计划状态、实际观察和接缝差异 | 前后片段、人物/物件、空间依据、声音版本、证据时间码、严重程度、修法和验收 |
| 提示词版本账 | PromptRevision、批准事件、审稿和反馈 | 各岗依据、风格版本、全文、字符数、变更、未决冲突、产出 Take |
| Take 实验账 | Take、任务输入输出、审片与返工比较 | 实际模型/参数、参考、可用区间、各岗判断、问题与假设、主要调整、对照结果和经验候选 |

字段类别核对依据为原仓库的[连续性账](https://github.com/MasterLeos/leos-six-department-directing-team-skill-v1/blob/main/assets/continuity-ledger-template.csv)、[提示词账](https://github.com/MasterLeos/leos-six-department-directing-team-skill-v1/blob/main/assets/prompt-version-log-template.csv)、[Take 账](https://github.com/MasterLeos/leos-six-department-directing-team-skill-v1/blob/main/assets/take-prompt-log-template.csv)。文件列在产品里改用可解析的记录 ID / file_id；下载台账时再渲染可读名称和来源链接。

各岗工作单共享场次设计内容，不建立六套可独立改写的副本。当前场次版本保存可编辑内容；任务、检查和素材记录保留固定执行依据。旧 revision 记录仅按其原身份读取。

### 4.7 提示词导演：编译产物及解释

编译输入是：已确认部门工作单、生成单元及其镜头/节拍覆盖、确定的参考素材包、项目风格版本、实际模型能力与显式参数。输出为完整执行文本，以及业务侧编译说明，包含输入版本、素材映射、有效字符数和关键决定的处理方式。

每项关键设计决定记录其去向：进入执行文本的哪个片段、交由哪份参考约束、如何转换为等效表述、或因能力/信息不足未能表达。该映射帮助追溯，不能作为模型确实会遵从的证明。说明不混入实际提交文本。

定义一个可测试的结构化纯文本编译格式，覆盖资产绑定、空间和对白约束、镜头范围、逐镜摄影与动作、微表演、环境活动及项目风格。对应原工作法的格式默认限制 5000 个非空白字符；目标模型另有限制时还需同时满足。其他模型专用格式必须有明确版本与差异说明，不能删掉栏目后仍称其符合原格式。[文本模板](https://github.com/MasterLeos/leos-six-department-directing-team-skill-v1/blob/main/assets/video-prompt-template.txt)

内部语义完整不等于每次将所有字段逐字塞进 prompt。图片输入重点表达某一选定时刻的布局、身份、构图和物件状态；视频输入重点表达随时间发生的动作、反应和摄影变化。不能把“递出前”和“递出后”的状态同时要求出现在同一首帧。

超出长度预算时先合并重复信息、减少无关修饰；关键状态和因果仍不能表达时返回调整生成范围或设计的建议。禁止静默截断后把版本标为可提交。[编译职责](https://github.com/MasterLeos/leos-six-department-directing-team-skill-v1/blob/main/references/prompt-director.md)

## 5. 审稿、裁决与授权是业务记录

ReviewPacket 固定设计版本、生成单元、PromptRevision 清单及参与岗位。清单中的每个 coverage_item 明确对应单元版本、提示词版本、计划镜头和被覆盖的动作范围；审稿行以 `packet_id + role + coverage_item_id` 唯一。同一计划镜头出现在两个不同试拍单元时分别审查，不能因 shot_id 相同而相互覆盖。

每份送审提示词将实际镜头出现项编号为 1 至 N，正式六岗审稿保留 6 × N 条记录；计划镜头 ID 和文本局部编号有明确映射。多个提示词组成批次时，按各自的出现项计算完整覆盖，不能省略重复出现镜头的不同版本。范围或编译结果改变时重建对应清单。

批量审稿要同时提供相邻镜头和共享场次依据，不能只把 N 次互不知情的单镜检查合并后宣称已经检查了接缝。单角色会诊只记录该角色；正式六岗审稿需覆盖整个范围。字段不适用可解释，不能用整行“不适用”躲过岗位审查。

结构校验、语义检查和人工取舍分开：字段/ID/范围错误是程序校验；设计冲突由模型或人工指出；艺术取舍由用户裁决。问题需保留观察、影响字段、修正建议和验收条件，重复问题的岗位视角先保留，再统一裁决。执行取舍前，用户须能按需查看这些信息以及建议/验收的来源与未知状态；摘要卡可以简化，但必须有完整详情入口，不能只在数据库保存。影响对象可用可读字段路径加工作单定位实现，不强制侧栏或自动跳转。审稿通过只是当前版本的结论，不是生成结果的保证。

冲突裁决保存冲突双方、各自意图、选择理由、采用的修改和拒绝的修改；字段归属不允许模型单方面改写其他岗位的已确认设计。LLM 生成“总导演通过”不能代替用户批准。

编译授权和视频提交授权分别登记，允许通过按钮一次性完成相邻步骤。按钮事件记录操作人、时间、对象版本和显示文案；如用户通过文字表达，则保留实际原文及来源。不能为填台账而虚构“用户授权原话”。

原仓库两项脚本分别检查文本标记/长度/镜头编号以及岗位—镜头覆盖。Jellyfish 应实现同类结构检查并增加 ID、依据版本和引用一致性检查；不会把脚本运行成功当作艺术质量通过。[文本检查](https://github.com/MasterLeos/leos-six-department-directing-team-skill-v1/blob/main/scripts/validate_prompt_text.py)、[审稿覆盖检查](https://github.com/MasterLeos/leos-six-department-directing-team-skill-v1/blob/main/scripts/validate_review_coverage.py)

## 6. 审片和返工产物

Take 审查状态单独区分未审/已审，主结论保留四种语义：`pass`（过）、`retain`（保）、`repair`（修）、`discard`（废）。其中“保”代表有值得保存的局部，不等同于整条通过；“修”可同时指定需要保留的好区间；结论与 TimelineClip 采用关系独立。

场次粗剪审查使用 CutReview，固定剪辑版本及涉及的 Take 区间。审片报告保存整体判断、已经成立的部分、必修/优化/后期问题、缺失覆盖、可用部分和待观察证据；不能只在镜头上放一个通过勾选框。

RepairItem 保存目标镜头/片段、问题时间范围、症状、根因假设、必须保留的内容、首选/备选修法、是否要新素材、下一次主要改动及验收标准。首版可作为审片报告内的类型化项目，采用后关联具体草稿/新任务；不额外建设通用任务管理系统。[审片与返工](https://github.com/MasterLeos/leos-six-department-directing-team-skill-v1/blob/main/references/review-and-repair.md)

在一条好视频局部有问题时，报告直接形成剪辑调整、补镜或设计修正建议。改动多个因素时记录无法单独归因，单次结果不能证明某一个词或参数必然有效。

## 7. 项目风格与知识候选必须有归属

ProjectStyleRevision 保存可执行的项目约定，规则包含负责领域、适用范围、可观察要求、例外、来源、确认人及状态。确认、候选、弃用、模型限定的规则分开；只有已确认且适用的规则进入新设计上下文，不自动更新已冻结方案。[风格资料结构](https://github.com/MasterLeos/leos-six-department-directing-team-skill-v1/blob/main/assets/project-style-profile-template.json)

KnowledgeCandidate 保存经验主张、适用条件、操作建议、反例/失败信号、例外、证据、可信程度和复核日期，按通用原则 P、当前操作条件 O、项目设定 C 分类。尚未证实的启发仍是候选，不因填写了 P 就获得通用规则地位。[知识与来源](https://github.com/MasterLeos/leos-six-department-directing-team-skill-v1/blob/main/references/knowledge-and-provenance.md)

已有分层版本流程支持从人工反馈、审稿和 Take 比较创建候选，人工确认项目风格规则；可录入有来源的会议文字作为候选依据。不实现自动读取所有会议、自动转录或自动改写全局 Skill。这些自动化缺失不应成为丢弃输出字段的理由。

声音设计同样保留在工作单与风格里：对白对象和版本、声源、环境/动作声、音乐约束、同期生成或后期处理方式。首版无音频生成或混音时，相关执行项标记“待后期处理”，不能凭文字设计宣称声音已经实现。

## 8. 用一个例子核对整条链

以下为 Jellyfish 方案示例，不是参考仓库的原文模板：

| 工作单 | 设计内容 / 记录 | 下游动作 |
| --- | --- | --- |
| 总导演 | B2：哥哥递借条，弟弟从敷衍转为回避；以弟弟反应为观察重点 | 安排递纸与反应的镜头覆盖 |
| 表演 | 弟弟听完借钱请求后，擦杯动作停住，目光落到纸上，再转向门口 | 视频中保留刺激、动作中断与目光变化的先后 |
| 镜内执行 | 后景店员继续收碗，不随兄弟同步转头 | 背景保持独立任务且不抢戏 |
| 摄影 | 摄影机留在桌子同侧，保持固定画面，杯子和弟弟手部可见 | 关键帧确定位置；视频保持机位并承载动作 |
| 连续性 | 纸张由哥哥手中落到桌面；弟弟手中的杯子仍在 | 相邻镜头继承同一关键物件状态 |
| 提示词编译 | 选定人物与空间参考，把上述已确认决定编入逐镜文本 | 保存提示词及每项关键决定的去向 |
| 审片 / 返工 | 反应成立，但后段纸张消失 | 标为“保”或“修”，圈定好区间，只补需要的纸张/过渡覆盖 |

单看“哥哥借钱，弟弟紧张，固定中景”会丢掉大部分设计。完整融合的验收重点是，这些可拍、可检查的决定能贯穿编译、审片和返工。
