## 1. 目标、范围与成功标准

单元画布改为“镜头依据 → 单元聚合入口 ← 参考素材”的浏览结构。进入单元后，以配置摘要卡和详情编辑呈现生产准备。导演和单元画布共用 graph 协议与图形组件，图的业务组织由后端负责。

| 范围 | 本次工作 |
| --- | --- |
| 导演画布、单元画布 | 迁移到同一基础 graph 契约；保留各自业务载荷、渲染器、编辑器和布局规则 |
| 后端公共能力 | 类型契约、身份与引用规则、图构建工具、完整性校验、共同契约测试 |
| 前端公共能力 | 图容器、悬浮导航、聚合入口与预览、布局状态管理；复用现有画布及工作台组件 |
| 四个画布共用的工作台 | 统一周期自动保存、手动保存、失败重试、并发保护及关闭页面后的恢复 |
| 指令画布、剪辑画布 | 复用上述保存修正，本轮不迁移其 graph |

成功标准：

1. 读取或保存响应提供可直接呈现的业务图；前端不再通过原始业务数组拼接节点、边、成员、摘要和业务准备状态。
2. 后端两个投影器使用相同的构建与校验工具；前端两个画布使用相同的图容器和导航能力，不各维护一套框架。
3. 全部镜头、单镜头和单元子图能连续浏览，筛选不改变单元身份和实际执行范围。
4. 配置编辑、参考准备、编译审稿与试拍入口保持闭环，六岗职责、历史版本和执行能力限制不被展示重构改变。
5. 保存失败、迟到响应、关闭恢复和版本冲突均不静默丢失用户输入，不允许旧内容覆盖新服务端版本。

不新增领域“草稿”、独立发布阶段、每次编辑的 graph 投影接口、通用表单引擎或第二套保存入口；不扩大跨镜头生成能力，不增加批量生成和自动采用。

现有 `test_scene_unit_design.py::test_first_application_preserves_independent_and_mixed_units_and_rejects_manual_target` 包含跨镜头单元保存与重读。本轮调查已运行该用例并通过，证明这不是仅存在于类型定义中的关系；该结果不代表本计划的实现验收完成。

改造前自动保存采用输入停顿触发，并限制持续编辑时的最长等待；发生保存错误后会停止自动保存。用户确认的新规则是每隔固定周期检查待保存内容，普通暂时性失败在下周期重试，具体规则见第 6 节。

## 3. 单元画布交互与领域边界

### 3.1 浏览与导航

- 左上角悬浮导航包含返回、前进、面包屑及“全部镜头／指定镜头”切换。镜头依据卡不承载筛选器。
- 总览展示镜头依据、相关单元聚合入口及每个单元的参考集合卡。依据卡沿用导演原文依据卡的阅读方式；单元入口沿用导演镜头聚合入口的交互。
- 点击单元入口进入独立子图，不在总览原地展开。面包屑为“单元画布 › 单元 07”，不把某镜头设为该单元唯一父级。
- 一个单元可出现在多个镜头筛选视图中，始终指向同一计划版本和 `unit_id`。子图显示该单元完整依据，不因入口镜头隐藏其他覆盖项。
- 返回时恢复此前镜头筛选、视口和缩放；后端提供视图成员，前端只切换到相应视图。

| 入口或操作 | 行为 |
| --- | --- |
| 从导演镜头进入 | 打开该镜头的单元浏览视图 |
| 正常进入单元画布 | 恢复当前版本上次筛选；首次进入展示全部镜头 |
| 精确单元链接／任务业务回跳 | 直接进入该单元子图，保留完整依据和固定来源 |
| 在全部镜头视图“AI 设计单元” | 明确选择目标镜头，再执行原有操作；手动创建入口移除，相关能力保留 |
| 在单镜头视图新增 | 使用当前镜头；已有单元编辑始终按单元身份定位 |
| 目标已删除或不可访问 | 明确显示目标不可用；不以同名对象或 `coverage[0]` 替代 |

### 3.2 配置卡片与参考

卡面提供当前编辑的摘要及明确的详情入口，详情承接该类别完整编辑，移除总设置入口。当前单元准备结论在顶部展开问题清单，提供重试及定位；生成指令操作独立保留。卡片拆分不改变存储模型和保存入口。

| 卡片类别 | 呈现内容与编辑边界 |
| --- | --- |
| 动作覆盖 | 按 coverage 项显示镜头、动作范围和显式执行选择，保留每个覆盖项的身份；不只读取第一项 |
| 生成配置 | 模型、时长、画幅、种子及额外参数，沿用既有模型能力与字段校验 |
| 组织要求 | 入幅、出幅、待准备参考要求；组织来源与理由放在详情中 |
| 前段依赖 | 固定来源、实际帧／落幅、绑定与复核状态，沿用已有依赖编辑器 |

每个单元有一个参考集合卡，总览显示缩略图、数量与问题，子图仍可查看和编辑这些参考。引用相同文件不等于同一绑定；各单元的绑定身份、用途、输入角色和顺序均保留。待准备参考要求与已绑定素材分别表达。素材作为输入，业务边方向为“参考 → 单元”。

新增只读“本单元执行依据”展示，通过镜头依据详情等现有详情入口访问。它消费已有 `unit_scope`／`resolved_design_fields`，区分执行、约束、背景、未解决项及视频、声音、后期阶段，并能定位来源字段。四类配置卡不机械改为六张岗位卡。

### 3.3 六岗与功能闭环

- 六岗仍为 `direction`、`performance`、`staging`、`cinematography`、`continuity`、`prompt`。声音是设计内容与制作阶段，不新增岗位。
- 导演负责设计，单元负责组织既定设计的执行。AI 单元组织不得为了适配卡片或模型而擅自改写镜头、摄影等设计。
- 单元执行范围由已有范围解析契约确定，不能由可见节点、连线、镜头筛选或共享对象出现位置反推。完整镜头的 `visible_result` 可作为背景，不自动变成每个部分动作单元都必须执行的内容。
- 编译审稿、模型预检、试拍继续使用原有业务服务校验。graph 完整、生成准备度、运行任务、素材审查和剪辑采用分别表达；图完整不构成执行授权。
- 多覆盖项单元保持可查看、可编辑、可保存，并显示当前执行能力限制；本轮不自动拆分、不复制为多个单元、不补造新的拍摄入口。
- 已确认内容和固定历史来源遵循已有版本规则。历史指令、Take 和依赖仍按原始身份阅读；当前对象删除不得导致历史记录被重新绑定。
- 参考准备 → 配置 → 编译审稿 → 能力检查 → 试拍沿用既有入口；成功生成只登记 Take，不自动采用，不改变实际覆盖和粗剪职责。

## 4. 后端 graph 契约与可复用标准

### 4.1 共同协议

导演与单元 graph 采用同一个基础结构，各自拥有强类型业务载荷。下表是契约职责；具体类名和响应字段名在实现时结合现有 OpenAPI 消费者收敛，不再形成新的产品决策。

| 部分 | 共同要求 |
| --- | --- |
| 图身份 | 明确图种类、场次版本身份与整数 revision；读取和保存响应中的内容与图属于同一快照 |
| `nodes` | 稳定节点 ID、节点种类、业务对象引用、展示载荷、来源及编辑目标；按节点种类区分载荷，不使用任意 `Any` 数据袋 |
| `edges` | 稳定边 ID、端点、关系种类及覆盖项／绑定／来源字段证据；业务关系与纯布局引导线分开 |
| `views` | 视图身份、成员、可见边、锚点、进入目标及层级；明确普通卡、聚合入口、只读引用等呈现角色 |
| `issues` | 共用 `code`、`message`、`severity`、`target` 结构；保留具体业务问题含义，不将所有状态压成一个“完整”布尔值 |

后端提供标题、编号、名称、摘要、计数、缺项、明确适用范围等业务展示内容。只返回 ID／路径，再由前端查原始数组拼标题和关系，不算完成迁移。前端可格式化单位、截断文字和选择具体渲染器。

对象身份与展示位置分离：同一单元可属于多个视图，但仍只有同一业务对象；视图引用对象不能生成新的单元身份。coverage、参考绑定等子项的操作目标必须精确定位，不能依赖标题或数组顺序猜测。

对于现有无稳定 ID 的历史项，明确标为 `stable=false`，其目标只在对应 revision 内有效；不在读取时生成并写入 UUID，不把临时路径伪装成长期身份。旧 revision 的临时目标不得套用到新内容。

导演现有 `placement`、`uses`、`applicability`、`paths` 保留自身领域语义，按导演载荷承接。单元配置不为了统一外形而被强行映射成导演设计字段。现有 `relationship_graph` 的详情、来源与检查消费者一并梳理，避免迁移画布后遗留另一套事实推断。

### 4.2 分层职责与共同工具

| 层次 | 可复用能力 | 边界 |
| --- | --- | --- |
| `app/core/contracts/directing` | 基础图 DTO、区分式业务载荷、身份／目标／问题类型及纯数据约束 | 不查询数据库，不编排业务数据 |
| directing service 共同读取上下文 | 固定当前内容和 revision，复用／批量加载来源、素材与能力证据 | 各领域授权和证据有效性仍由已有服务判断 |
| 共同图构建工具 | 注册节点与边、加入视图和问题、建立索引、检测重复冲突、完成时统一校验 | 可以是少量函数或小型 `GraphAssembler`；不引入插件系统、继承框架、反射路径引擎 |
| 导演／单元投影器 | 各自业务映射、成员、筛选视图、分组、摘要、状态与来源组织 | 复用既有范围和准备校验；不各自重写基础构建与完整性规则 |
| API 层 | 收参、鉴权、调用服务、组织响应 | 不拼装节点、不在路由中实现业务规则 |

若采用 `GraphAssembler`，公开接口以 `add_node`、`add_edge`、`add_view`、`add_issue`、`finish` 等少量动作即可。价值在于统一身份注册、引用检查和完整性约束，不是仅给字典追加操作套一层类。构建工具自身不做 I/O 或鉴权。

共同完整性校验至少覆盖：

1. 节点、边、视图 ID 唯一；重复定义冲突可诊断。
2. 边端点、视图成员和视图中的边均闭合；视图可见边的两个端点可在该视图定位。
3. 业务对象引用一致，视图父级无环，聚合入口指向有效子图。
4. 锚点、来源、问题定位和编辑目标有效；外部或历史目标明确带来源上下文，不能当成本图成员误验。
5. 内容、图和目标的版本／revision 一致；历史固定来源的版本另外显式表达。

缺失引用显式形成缺失状态或问题，不静默删边伪造完整。权限、模型接受能力等业务判断由领域服务负责，不能仅因结构校验通过就认定可操作。

### 4.3 读取、保存与证据时效

在现有场次版本读取及保存响应中提供两类 graph，同一响应中的业务内容和 graph 以同一版本及 revision 为准。graph 是派生结果，不另外持久化为第二份业务事实，不接受前端上传节点／边作为业务写入。

复用当前业务加载及检查流程。模型、文件和前段落幅可能在场次 revision 不变时发生变化；加载失败或证据未验证时明确表达未知／失败，不能沿用旧“可执行”结论。最终编译、检查及试拍仍重新验证实际输入。

本轮不新增每次编辑触发的只读 graph 投影接口。图生成失败时展示错误与恢复入口，不回退到前端重新拼图。读取或保存请求的未知结果仍按第 6 节恢复，不能因图响应失败就丢弃本地输入。

## 5. 前端复用与状态边界

| 现有入口 | 复用或提取内容 | 保留业务专属内容 |
| --- | --- | --- |
| `front/src/components/canvas/Canvas.tsx` | `useCanvasViewport`、`CanvasCard`、`CanvasDragHandle`、`CanvasEdge`、`CanvasNodeFrame` 及几何能力 | 不引入业务判断 |
| `DirectorCanvasSurface.tsx` | 提取共同图容器：视口、小地图、聚焦、适配视图及节点／边容器 | 移除公共层内的导演分组、ID 前缀推断、中文关系标签分类和专属焦点选择器 |
| `DirectorDesignCanvas.tsx` | 提取返回／前进／面包屑导航和浏览历史能力 | 业务跳转命令、详情编辑和导演语义保留在业务层 |
| `DirectorShotEntry.tsx` | 聚合入口外壳、只读子图预览 | 预览消费真实 graph 视图成员，计数来自后端，不再独立拼图 |
| `useDirectorLayout.ts` | 共同布局缓存、手动位置、重排及撤销状态 | 导演排布规则和旧缓存迁移留在导演适配逻辑中 |
| 工作台已有组件 | 主题、按钮、详情和正文预览；参考选择／预览、来源、前段依赖等业务组件 | 业务组件维持现有绑定、上传、历史来源和编辑校验语义 |

共同容器通过强类型节点种类分派具体渲染器，并穷尽处理支持的种类；不把后端 schema 变成任意动态表单。后端决定业务成员和关系，前端决定坐标、卡片尺寸、缩放、布局及本地导航状态。

聚合预览和进入后的子图使用相同的成员与布局解释。预览不修改用户浏览历史或布局缓存。布局缓存按用户、项目、场次、版本、视图隔离；稳定节点保存后的 revision 变化不应重置手动位置，无稳定 ID 的历史项遵守 revision 边界。

### 保存前的显示

工作台维护“已确认服务端基线”和“当前编辑内容”。单元 graph 通过后端只读预览消费当前编辑，其余画布 graph 仍对应保存基线；配置详情和输入控件读取当前编辑。后端旧卡片载荷、刷新响应和保存响应均不得直接覆盖当前输入。

- 本地变更尚未保存时明确提示图待同步；不能把旧摘要和旧准备度呈现为当前输入已经核验的结论。
- AI 方案明确应用后新增单元并更新当前编辑的后端只读投影，保存前即可进入各配置卡片；保存失败、恢复及撤销重做保留当前卡片，不为了显示节点强制提前保存，也不由前端构造临时业务 graph。手动创建仅移除界面入口，相关能力保留。
- 本地已移除或调整的目标不能从旧图误编辑到其他对象；按明确身份核对当前编辑内容，必要时提示图待同步和目标当前不可用。
- 保存成功后使用服务端返回的 graph 更新图基线；若用户又有新输入，仍保留当前编辑，并以当前内容重新读取单元投影。准备状态区分核实中、失败与齐备，不借用保存状态。

## 6. 四个画布共用的保存、重试与恢复

复用 `CanvasSequenceWorkbench.tsx` 和 `DirectingStore` 的保存协议及恢复机制。`version_id` 确定版本，整数 `revision` 表达该版本的并发基线，`request_id` 标识一次确定内容的保存请求；不新增另一个 `revisionid` 领域对象。

### 6.1 周期与队列

默认每 **5 秒**检查当前是否有未保存变更。无变更不请求；有变更且无在途保存才提交。手动保存进入同一个串行队列，不与自动保存并发。周期调度不要求用户停止输入，也不增加配置页面。

提交时固定 `expected_revision`、`request_id` 和发送内容。保存过程中允许继续编辑；响应核对版本、revision、请求身份、已提交内容及 graph 后，只推进确认基线，不替换用户更新的当前内容。

例：以 revision 8 提交 A；请求途中用户改为 B；A 成功返回 revision 9 和 graph A。确认基线更新为 A／9，当前输入仍是 B；下一次保存以 revision 9 提交 B。不能把 A 覆盖回编辑器，也不能误将 B 标为已保存。

### 6.2 不同失败分别处理

| 情况 | 行为 |
| --- | --- |
| 网络等暂时性失败 | 持续显示失败提示并保留输入；允许手动重试或下个周期自动重试 |
| 请求结果未知 | 保留原 `request_id + expected_revision + 发送内容`，先验证结果或原样重放；不能把之后的新输入混入原请求 |
| 原请求重放／验证成功 | 先推进确认基线；更新的本地输入仍待保存，再以新 revision 和新请求提交 |
| 内容校验失败 | 显示具体字段问题，等待修改后再尝试；不每周期重复发送相同非法内容 |
| revision 冲突 | 使用已有显式冲突处理；不盲目重试，不自动用本地覆盖服务端 |
| 响应不满足保存契约 | 不认定当前内容已保存，保留输入及必要的在途证据，进入结果核验 |

后端目前保留最近一次保存请求的幂等信息，并非任意历史请求账本。若另一保存已经推进服务端版本，旧请求不能被当作当然成功，继续走冲突／恢复规则。已有“保存并生成”等在途操作重放仅恢复原授权和原请求，不自动发起新的生成任务。

### 6.3 页面关闭与恢复

沿用现有本地持久化，保存确认基线、当前编辑内容及必要的在途请求信息；保留现有对尚未处理恢复记录的保护，不无条件覆盖另一版本的恢复内容。重新进入先核对最新服务端版本，再恢复或进入现有冲突处理。

服务端未更新的数据不能覆盖可恢复的本地输入；服务端已更新时也不能直接提交旧本地内容。不能用布局缓存、graph 快照或展示选择代替编辑内容恢复。浏览器存储不可用时明确提示恢复能力受限，不能声称内容已保存到服务端。
