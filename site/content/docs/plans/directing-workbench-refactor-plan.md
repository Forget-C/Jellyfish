## 1. 结论与选择依据

推荐“以场次组织创作，以早期粗剪验证效果，以生成单元执行试拍”的流程。六部门参与设计、检查和诊断，工作台不按六个部门排成六道串行审批。

```text
章节原文 → 场次与创作意图
              ↓
         导演设计 ↔ 关键资产与空间验证
              ↓
         镜头覆盖与节奏预演
              ↓
         编排生成单元、参考和执行方案
              ↓
         关键试拍 → 审片与逐步形成粗剪
              ↑                 ↓
              └── 定点修改/补拍 ─┘
                                ↓
                    场次验收、章节组合
```

这是一项设计判断，并非已测得的质量结论。评估标准是叙事连贯性、问题能否早发现、人工操作负担、可追溯性、返工范围和实现复杂度。

参考六部门工作法提供了共享场次事实、设计先于编译、逐镜审稿与局部返工的方法；生成控制也允许按空间和戏剧小节组织生成范围。本文吸收这些方法，不将聊天步骤原样当作产品流程。[工作协议](https://github.com/MasterLeos/leos-six-department-directing-team-skill-v1/blob/main/SKILL.md)、[生成控制](https://github.com/MasterLeos/leos-six-department-directing-team-skill-v1/blob/main/references/generation-control.md)

## 2. 四种流程比较

下表是定性评估，不是基准测试得分。

| 方案 | 优点 | 主要问题 | 判断 |
| --- | --- | --- | --- |
| A：先拆镜，再逐镜补资产和生成 | 简单，适合孤立素材 | 故事和空间过早切碎；逐镜重复准备；接缝问题后发现 | 不作为叙事主线，可保留独立实验入口 |
| B：完整六岗依次审批，全部批准后批量生成 | 分工与文档完整 | 多轮填写/批准；纸面自洽不代表模型能实现；实际反馈晚 | 采用工作单标准，不采用串行审批形态 |
| C：先大量生成，再在剪辑里寻找故事 | 探索自由，可发现意外好片段 | 缺少统一身份、空间和叙事依据；成本难控 | 适合有范围的风格探索，不作为剧情主线 |
| D：场次设计与视觉验证迭代，试拍后立即粗剪 | 保持叙事整体，早暴露问题，可局部保留和补拍 | 需要单元、版本和最小剪辑能力 | 推荐，先验证一场戏的纵向闭环 |

D 的价值在于高成本决定发生前已有依据，失败后能准确回到应修改的层。采用固定业务服务与明确实体控制复杂度，不建设任意可编排的工作流引擎。

## 3. 放弃旧流程的哪些前提

| 此前前提 | 新决策及原因 |
| --- | --- |
| 编辑页负责准备，工作室负责生成，必须来回跳转 | 同一场次工作区提供设计、试拍、剪辑视图；服务职责仍分离，页面服务连续创作 |
| 先完成资产提取确认，再设计场次 | 先明确意图，已有资产提供约束，新资产随设计补齐，避免预先精修无用资产 |
| 先确定所有分镜 | 先节拍与覆盖，经过预演和试拍调整镜头；分镜是表达方案，不是唯一提取答案 |
| 一镜对应一次生成 | 生成单元可覆盖一镜、多镜或指定动作部分，生产粒度由需求与能力决定 |
| 视频全部生成完才剪辑 | 早期预演、滚动粗剪，依据实际节奏和接缝决定补拍 |
| shot.status = ready 是生成核心门槛 | 按本单元需要的事实、设计、参考和参数判断；不要求必须先跑提取任务 |
| 六部门各需要用户批准一次 | 完整保存专业输出，集中确认创作取舍和执行范围，避免把后台检查变成用户负担 |

这些是目标变更，尚未改变当前系统。实施时再同步 AGENTS.md 与当前架构，不提前把计划写成事实。

## 4. 新主流程

### 4.1 场次与创作意图

章节仍是用户定义的故事段落；场次是相对连续时空内的一次具体事件。确认本场改变什么、主要视点、关键节拍和不可改事实。输入可以是原文、剧本、用户补充或已有镜头，AI 划场只产生草稿。

输出：场次范围、叙事意图、节拍草案、事实及待核验点。单场章节直接进入工作区；未知信息只有影响当前决定时才要求补齐。保留原文快照和范围版本，正文改变后识别失效。

### 4.2 导演设计与视觉依据共同迭代

总导演和用户确定人物目标与场面变化；表演、镜内执行、摄影协同细化；场记建立计划状态。已有场所布局、角色造型和项目规则用于检查动作与空间是否成立。

新资产按本场需求创建。多人关系不清时先使用文字锚点、简单关系图或低成本构图验证；已有造型直接引用，不重复生成。视觉验证可以改变设计，设计也可提出资产修改建议。本场临时伤势、物件损坏等状态属于场次，不能静默改写全局资产。

输出：共同设计草稿、资产需求、视觉依据、冲突和验收标准。用户对汇总方案集中裁决，各岗不得各自改写剧情。

### 4.3 镜头覆盖与节奏预演

根据节拍选择建立、关系、动作、反应、细节和过渡等覆盖。用文字卡、已有素材或静态分镜形成可排序预演，标注预计时长、对白/动作落点和缺口。预估时长与素材实际时间分开。

先判断本场是否讲清、重点是否可见、反应是否有时间发生，再投入生成。简单场次可以快速完成预演，不强制生成全套精修分镜图。输出镜头覆盖和预演顺序，后续允许调整数量，稳定 ID 保留变更来源。

### 4.4 编排生成单元

生成单元定义“一次希望模型拍出什么”，包含目标节拍/镜头范围、空间、连续动作、入口/出口、模型、方式、参考、参数及验收要求。

划分依据：动作连续性、空间稳定性、切镜控制能力、当前模型限制、参考/文本预算和重拍成本。镜头、生成单元、剪辑片段允许不同粒度，不强制一一对应。

例如一场借钱戏有四个计划镜头，连续双人表演可以组成一个单元，关键道具动作独立试拍，反应覆盖另行补充。若模型无法可靠实现多镜范围，提交前明确拆成多个单元并更新计划，不在执行时偷偷拆分。

此时固定实际输入文件，再编译对应提示词。可以使用纯文本、角色/场所参考、构图帧、首尾帧或表演参考；方式由单元需求和模型能力决定，首帧—关键帧—尾帧不是统一必经工序。

### 4.5 有目的试拍与滚动粗剪

优先试拍最能决定本场是否成立的单元，例如多人关系、关键动作或情绪转折。试拍是执行优先级，不是绕过批准的后门；本次验证目标、范围和输入必须明确。

结果进入候选，按“过、保、修、废”审片。好区间进入粗剪，观察真实表演和接缝，同时推进无硬依赖的其他单元。依赖前段实际落幅的单元等待相应素材确认；只依赖计划状态的单元可先试拍。

原 Take 整条保存，不因局部采用而裁掉源文件。模型实际切镜与计划不符时记录真实区间及差异，不能按计划秒数假造实际边界。首版允许人工标注，不依赖自动切镜算法。

### 4.6 缺口驱动补拍与验收

以粗剪问题决定下一步：调整入出点/顺序、换已有 Take、补反应或过渡、局部重拍，必要时回到设计。验收看本场是否讲清、表演是否成立、关键空间和动作是否可信、片段能否连接，不以镜头卡全部变绿为标准。

通过后组合进章节并检查跨场衔接。声音设计与实际完成状态分开，缺少声音执行能力的项目标记待后期处理，不因画面完成就宣称成片完整。

## 5. 资产与参考素材的时机

| 时机 | 使用方式 | 是否直接进入模型输入 |
| --- | --- | --- |
| 理解场次 | 识别角色、场所、关键物件，关联已有资产 | 否，先建立事实关系 |
| 导演设计 | 使用空间/造型依据，按需补设定、关系或构图验证 | 验证任务按需使用，不代表后续全部使用 |
| 预演 | 草图和已有图片检查构图、视点与节奏 | 不要求精修或固定整套参考 |
| 准备生成单元 | 确定 file_id、用途、主体绑定、顺序和来源 | 是，编译前固定本次素材包 |
| 后续补拍 | 选用原资产、要保留的设计和实际连续性资料 | 显式选择，不自动继承所有上一轮文件 |

不设“全项目资产全部完善才能开工”的门槛，也不等到视频生成前才检查场景是否支持调度。素材只承担明确主要用途，静态身份、场所空间和连续性状态分开。

从采用区间提取连续性帧时生成独立图片文件，保存来源 Take 和真实时间码。模型不支持某用途或媒体时显示缺口，不静默丢弃。换默认资产图不替换已固定参考；用户选择更新后才影响相关草稿和确认。

## 6. 六部门与用户确认

| 阶段 | 主导与参与 | 用户重点查看 |
| --- | --- | --- |
| 创作意图 | 总导演主导，场记核对事实 | 本场意图、关键变化、待决定问题 |
| 设计与预演 | 表演、镜内执行、摄影协同，总导演裁决 | 可编辑场次方案、镜头覆盖、冲突 |
| 单元准备 | 提示词导演编译，场记登记，六岗审查 | 本次拍什么、参考什么、最终文本和问题 |
| 审片粗剪 | 总导演判断整体，各岗诊断，场记记证据 | 可用区间、接缝、最小修法 |
| 经验更新 | 场记组织证据，用户确认项目规则 | 有适用范围的风格和经验候选 |

岗位是专业职责，不预设六个常驻 Agent。工作单完整存储，简单场景允许有理由的不适用项，后台可按阶段批处理。单角色会诊不虚构其他岗位通过；正式联合审稿仍保存六岗 × 本轮镜头覆盖，提供共同场次与相邻依据，用户不逐格签字。

集中确认两个主要决定：本轮创作方案，以及本次执行的单元与输入。连续操作且无新冲突时可在一个交互中完成，后台分别记事件。采用片段也是显式创作动作。只有语义、参考、范围或参数等实质变化影响相关确认，非执行备注无需重审。

## 7. 界面结构

采用项目导航、场次工作区与持续可访问的预演/粗剪视图：

- 项目导航：章节与场次、资产、项目设定、文件。
- 设计视图：原文/节拍、空间与表演、镜头覆盖；六岗详细工作单按需展开。
- 试拍视图：生成单元、参考包、提示词、任务与 Take 对比。
- 剪辑视图：明确区分预演项和真实素材，调整顺序/区间，检查接缝和缺镜。
- 问题侧栏：按影响及下一步动作汇总，点击定位可修改对象。

三视图共享场次和选择，不强迫用户在旧 ChapterShotEditPage / ChapterStudio 间跳转。同一区域可以编辑设计草稿和参考，后端仍区分事实、设计确认、执行和采用，已批准版本不原地改写。

任务中心继续仅展示通用运行信息。这是任务与业务的职责区分，独立于旧分镜流程，仍值得保留。

## 8. 业务模型：设计、生产、剪辑分别表达

| 对象 | 职责与关系 |
| --- | --- |
| Project / Chapter / Sequence | 项目、故事段落、具体场次；Scene 仍指场所资产 |
| SceneDesignRevision | 意图、事实依据、六岗工作单、节拍、空间、镜头覆盖和风格依据；共用 beat/shot/anchor/event ID，确认后不可变 |
| Asset / ProjectStyleRevision | 可复用设定；场次临时状态留在设计和观察，不污染资产 |
| ProductionPlanRevision / GenerationUnit | 如何分次生成；单元覆盖一镜、多镜或节拍范围，定义需求/依赖，引用设计版本 |
| PromptRevision / ReviewPacket | 单元最终文本、媒体、参数、编译说明、审稿和确认；逐镜审查保留原作用域 |
| Take | 单元的一次成功产物，TaskOutput 唯一关联；不强制唯一 shot_id |
| TakeCoverage / TakeReview | 实际镜头/动作区间、证据、结论和问题；实际覆盖与计划覆盖分开 |
| SequenceCutRevision / CutItem | 预演与粗剪；planned 项引用设计，media 项引用 Take 区间，使用不同类型 |
| RepairItem / KnowledgeCandidate | 局部修法与经验，关联问题、保留范围、新计划和结果 |

Beat/Shot 是设计中的节拍与覆盖单位，不是任务的父容器。初期可将工作单、单元和审查项目保存为类型化结构，不为每字段建表。已有 Shot 如保留，仅作为稳定身份/查询索引，不能再维护独立可写的摄影真值。

统一使用 GenerationUnit，不另设同义 GenerationSegment。一次单元提交对应一次明确的模型请求，需要拆为多次请求时先修订计划。一个镜头可由多个单元提供不同覆盖，一个 Take 也可提供多个实际镜头或动作区间，剪辑从实际结果选取。

首版就支持这些关系、人工区间标注和单元级 API，不把 Take 绑死镜头表。实际多镜执行由接入模型和验证结果决定；不支持时显式拆分或提示更换模型，不宣称任意模型都能精准切镜。

预演预计时长与素材实际时长分开。粗剪使用毫秒级 source_in/source_out 与 timeline_start，校验 0 <= in < out <= 文件时长。首版支持主视频顺序播放、排序、区间调整和保存，不宣称专业级帧精确回放或成片渲染导出。替换预演项为素材项必须显式选择，不让候选结果自动进入时间线。

## 9. 状态、版本与并发

目标系统不继续以提取任务完成定义 shot.status = ready。独立展示事实核对、设计确认、单元可执行性、运行任务、素材审查、粗剪验收。旧 shot.status 及依赖入口在切换时移除，不保留 ready 兼容别名。

事实可人工录入或自动提取后确认，只阻断当前单元必需且缺失/冲突的信息。原文与设定说明故事事实，设计说明计划怎么拍，Take/剪辑说明实际拍到和采用什么；拍错剧情不能自动改写原文，需标记不符或经明确创作修订采纳。

| 变更 | 影响 |
| --- | --- |
| 修改叙事或空间依据 | 相关设计需确认，依赖旧设计的未提交单元待更新；保留旧 Take |
| 修改单元文本、参考、范围或参数 | 新版本，更新相关审稿/确认 |
| 资产库新增默认图 | 仅提示可选更新，不替换冻结文件 |
| 引用文件不可用 | 阻止依赖它的提交，列出具体缺口 |
| 替换前段采用区间 | 复查实际相邻接缝与落幅依赖，不重跑全场 |
| 在途结果完成时设计已变化 | 旧依据候选，不自动采用 |
| 改非执行备注 | 不影响执行确认 |

首版可在相关设计版本范围内保守标记待复查；通过单元引用和实际相邻关系定位影响，不建设通用依赖图引擎。版本检查与任务创建保持一致事务边界，重复提交使用幂等键；明确再次试拍可创建新任务。

迟到 AI 输出遇到人工更新时保存建议，不覆盖草稿。TaskOutput 唯一关联防止重复 Take；发布和技术重试不自动采用。创作返工记录原因和主要调整，网络/供应商错误沿用技术重试机制。

## 10. 执行底座与接口

保留有用的文件/媒体引用、模型适配、任务执行/取消、结构化模型输出、独立编译和 OpenAPI client。它们提供执行基础，不决定用户创作顺序。

目标链路为场次设计 → 生产计划/参考 → 编译/审查 → 单元提交 → 统一生成执行 → Take 归档 → 审片/剪辑。API 按场次、设计版本、生产计划、单元、提示词、Take、粗剪组织，不沿用镜头槽位作为视频提交与采用目标。

提交只接收已确认版本与幂等身份，服务生成最终载荷，不另收未审文本。所有入口校验项目归属，业务检查不能只在前端。批量受理固定单元与版本清单，先预检；无依赖单元独立运行，素材依赖未满足的项不受理，明确告知需要先完成什么。

通用 GenerationEntityGate 保持实体与媒体检查；场次规则、模型可执行性和依赖由相应服务处理。capability、target、终态交付注册新单元/Take 目标，Publisher 只归档候选，采用使用粗剪版本比较。长耗时设计、编译、审稿复用异步任务，固定服务负责阶段衔接。

跨层 DTO 放 app/core/contracts，tasks 不定义导演 DTO，integrations 不依赖任务类型。执行不能静默改模型、拆单元、丢素材或二次改写批准文本。模型能力必须单独验证，模拟结果只能验证业务关系。

## 11. 实施范围与顺序

先做一场戏的纵向闭环，再扩展完整项目管理，避免先建齐所有表单才验证生成和剪辑粒度。

以下为阶段概要，实际执行按[任务清单 T01–T18](/docs/plans/directing-workbench-implementation-tasks/)推进。阶段核心关系先用隔离用例验证，真实模型能力在首次试拍接入时验证并记录；不能用模拟结果宣称真实生成通过。

| 阶段 | 工作 | 验证与交付条件 |
| --- | --- | --- |
| P1 核心关系与执行验证 | 设计/单元/Take/剪辑契约；一镜多次试拍、多镜单元、人工区间与模型能力验证 | 隔离用例证明关系不一一绑定；真实模型验证独立记录 |
| P2 最小场次闭环 | 同一工作区编辑设计、复用资产、建单元、编译/审稿、试拍、选片与保存粗剪 | 一场戏从方案走到真实粗剪并能补拍；关键六岗结构和批准追溯接通 |
| P3 设计与视觉验证 | 完整工作单、风格、按需资产生成、关系/构图验证、预演卡 | 资产由设计驱动；预演可暴露覆盖缺口；参考与设计同源 |
| P4 生产与接缝 | 单元重组、独立项批量执行、提帧依赖、实际覆盖和跨单元审查 | 多镜结果不写入多个镜头槽位；迟到结果不自动采用；依赖更新正确 |
| P5 章节与反馈闭环 | 场次验收、章节顺序播放、返工、三本账、风格/知识候选 | 采用片段可追到设计和输入；保留好片段，只补必要部分 |
| P6 切换与完整验收 | 删除旧入口/状态/重复字段，同步接口/文档/AGENTS，完成对照样例 | 新流程独立运行，无旧旁路；效果和限制有记录 |

P2 是最小可试用闭环，P6 才是首版全部完成。专业剪辑、自动切镜、自动视频理解、自动会议提炼、全局知识自动更新和成片渲染导出不纳入首版。预演、真实素材顺序播放和保存必须实现，不能用占位按钮代替。

资产复用和人工输入首轮必须可用，资产精修管理后补。人工播放和区间标注足以验证核心闭环，不把自动视频理解当作前置。

## 12. 验证是否更合理

先做流程原型，再在相同原文、资产基础、模型和预算范围比较 A 与 D。样例包含双人对白、道具交接、多人反应；查看实际视频和粗剪，记录随机性与操作者熟悉度，不把少数试验当作普遍结论。

| 指标 | 观察方法 |
| --- | --- |
| 首个可判断粗剪出现时间 | 从进入场次到可以连续检查叙事，预演与真实粗剪分别记录 |
| 人工操作负担 | 重复确认、页面往返、重复编辑事实的次数与耗时 |
| 采用素材成本 | 实际采用素材的请求次数、费用与耗时，使用可取得的真实记录 |
| 叙事与连续性 | 按预先确定要求检查信息、反应、空间、物件和接缝 |
| 返工范围 | 局部问题影响多少单元，是否能保留有效区间 |
| 可追溯性 | 能否从问题片段找到设计、参考、提示词及改动原因 |

最低流程验收：无关缺口不阻断整场；人工采用不被覆盖；可以从粗剪定位并只补一个反应或动作部分；适用六岗输出可查看并被下游使用。若新流程只增加填写负担而未提前发现问题，应简化交互或试拍范围，不继续堆审批。

技术用例覆盖跨项目引用、原文失效、AI 覆盖人工、单元重组、参考映射、审稿漏项/混版、重复提交/回调、在途结果、取消、计划/实际覆盖不一致、区间越界、并发采用和依赖变更。

实施后端运行相关测试，交付节点执行不调用外部模型的回归；前端 API 变化后运行 pnpm run openapi:update，并至少通过 pnpm exec tsc --noEmit；文档通过 Hugo 构建。真实模型验收单独记录输入、费用和结果，结构测试不代替成片判断。

## 13. 切换与文档责任

可直接改变旧 API、ShotDetail 摄影字段、shot.status、视频生成目标和页面结构，不做双写或兼容层。数据库通过 Alembic 发布，在隔离开发库验证。现有数据不自动清除，删除需有明确执行范围。

清理旧章节直接拆镜主入口、重复准备操作、镜头视频自动采用、单镜产物绑定、提示词二次追加旁路和占位剪辑。新系统设计版本与原 Take 保持追溯，这是产品功能，不是兼容旧系统。

实施同步更新当前架构的页面、状态、生成与发布说明，以及 AGENTS.md 主流程。API 收参/鉴权/响应、服务负责业务、任务中心保持通用等工程边界继续保留。
