## 当前实施状态

已完成的实现以 [数据库迁移与系统种子](../../architecture/database-migrations/) 为准。本计划只保留仍有意义的实施状态和后续工作，不继续推进已撤销的旧库自动登记方案。

已完成：

- 异步 Alembic 配置、初始 schema 与后续 revision 链。
- 空库和已纳管库统一执行 `upgrade head`；非空未纳管库直接拒绝，不按 ORM 表名猜测版本或自动 stamp。
- Compose 的 `backend-migrate` 与 `backend-seed-system-data` 一次性服务，API 和独立 task-worker 等待它们成功。
- `init_db.py` 调用正式迁移入口，应用初始化不再使用 create_all。
- 系统提示词 seed 独立执行，操作范围限于系统模板，保留用户模板。
- 历史运行数据 reconciliation 已放入版本迁移，旧 SQL 不再按目录扫描执行。
- `13b6a9d2e401` 将旧执行表收敛为 tasks、task_inputs、task_outputs，并调整 files 和 file_usages。此迁移不转换旧任务历史；新任务历史从新表形成。

## 验证证据与部署边界

完整 revision 链已在独立 MySQL 9 容器中执行到 `f2a3b4c5d6e7`，插入测试文件后再升级到 `13b6a9d2e401`，确认文件 ID 和对象 key 保留。任务与文件范围的实际结构和 ORM 比较通过；多连接领取和终态竞争测试通过。验证容器已移除，没有升级现有开发库或生产库。

本地迁移测试覆盖：

- 新任务表列与索引匹配当前模型。
- 文件 key 唯一，跨项目引用不再相互覆盖。
- 重复或过长的已有 key 在任何 DDL 前被拒绝。
- 非空未纳管数据库不被自动登记。

SQLite 测试不替代 MySQL DDL 和行锁验证；MySQL 测试不调用真实供应商或对象存储。

## 待完成

1. 在实际目标环境核对当前 Alembic 版本、文件 key 约束和部署配置，再按停机升级顺序执行。该步骤尚未完成。
2. 将系统提示词 seed 从遗留 SQL 收敛为版本化数据包及显式 upsert，并保留重复执行和用户模板保护测试。
3. 完成目标环境版本盘点后整理 `backend/sql/002`—`008` 等历史资料；不再把这些 SQL 放回启动链路。

系统 seed 数据包整理独立于任务体系收敛，不作为本次任务改造的额外功能范围。

## 升级与回退约束

升级前停止 API、新旧 Worker，并备份数据库；随后运行迁移、系统 seed，再启动新 API 和独立 task-worker。新旧任务执行代码不能混跑。

非空未纳管库须先由维护者核对完整结构并显式建立正确基线，或使用新的空库。禁止直接 stamp head 来掩盖缺失的结构变更。

收缩迁移删除旧执行历史，不提供 downgrade。MySQL DDL 不是整段事务；失败后需核对已完成步骤，回退依靠数据库备份及对应旧代码。文件字节不由迁移删除。
