# 场次划分统一编辑与历史版本计划

> 状态：代码实现与验收已完成（2026-09-30）。P1–P6 与 V01–V18 的证据见末尾。业务数据库尚未升级；本次交付包含独立迁移和显式接入命令，不包含生产部署或收费模型调用。
>
> 承接[章节入口与整章划分工作流优化计划](/docs/plans/chapter-division-workflow-plan/)。前序完成状态及验证记录保留；本计划实施后替换其 AI／手动双视图和分散历史入口，继续复用整章草稿、原文选区、影响预览、原子保存及身份保护。
>
> 用户要求：顶部右侧只保留“AI智能划分”和“历史版本”；AI 与手动使用同一编辑组件；历史以 Modal 内可展开表格呈现；AI 完成后回填编辑区，保存形成新版本并切换至该版本。

## 1. 现状与设计依据

以下为本轮改造前的设计依据；改造后的当前事实见架构文档和末尾验收记录。

| 当前事实 | 可复用部分 | 本轮补齐内容 |
| --- | --- | --- |
| “章节活动”已经列出场次分析任务 | 任务身份、状态、时间及成功分析结果；任务输入冻结原文、原文版本和分析时成员基线 | 将列表升级为统一历史入口，补齐业务展示字段、分页及按需详情 |
| AI 结果包含场次名称、摘录等建议 | 每次成功分析可以作为可追溯的方案记录 | 明确“待保存方案”，记录它与最终保存版本的关系 |
| 用户调整 AI 结果后另行保存整章 | 现有本地草稿、范围验证和事务保存 | 保存调整后的最终快照，不能用原始 AI 输出代替用户保存结果 |
| 纯手动保存不会生成分析任务 | 同一整章提交能力 | 手动保存也进入历史列表，不创建虚假的 AI 任务 |
| `DivisionCommit.response` 包含提交时快照 | 响应丢失恢复及可验证的旧保存记录 | 业务版本身份、展示编号、来源、当前版本指向和历史查询 |
| `Sequence.version` 是对象并发版本；`is_current=false` 表示退出的场次 | 成员并发校验、历史身份及成果保留 | 章节划分版本独立表达，不能把对象版本或退出列表当作完整划分历史 |
| 管理详情仍可单独改名／调序 | 已有基本信息编辑入口和章节锁 | 所有影响划分的写入同步记录版本，避免当前版本与实际成员不一致 |

结论：现有场次分析列表具备方案历史的基础，可以直接复用。需要补齐最终快照、手动变更和当前生效关系，不另建重复的分析任务系统，也不把所有任务状态都计为正式版本。

主要实施位置：

- 前端：`ChapterSourcePanel.tsx`、`ChapterSourceSelection.tsx`、`chapterDivision.ts`、`SequenceDetails.tsx`、`ChaptersTab.tsx` 及相关样式。按职责拆出统一编辑组件和历史 Modal；不改造无关页面。
- 后端：`contracts/directing/division.py`、`models/directing.py`、`services/directing/division.py`、`workspace.py`、`ai.py`、directing API 及必要 Alembic 迁移。
- `DirectingTasks.tsx` 被其他工作台使用；本轮替换划分页中的使用方式，不删除其他业务需要的任务展示能力。

## 2. 范围与成功标准

本轮交付：统一划分编辑器、两个顶部操作、可展开历史表格、AI 安全回填、不可变保存版本、历史查看／恢复、旧数据接入及相应验证。

成功标准：

1. 普通划场、首次划场和明确范围编辑均进入同一编辑区，打开页面不自动分析或保存。
2. 顶部右侧只有“AI智能划分”“历史版本”，移除模式切换、章节活动、查看过期结果、继续确认结果等重复入口。
3. AI 结果回填同一草稿，用户可直接修改；保存后产生唯一新版本并留在页面，刷新仍能读取该版本。
4. 历史表格涵盖现有分析记录及手动／AI／历史恢复的保存版本，展开行能核对场次内容。
5. 查看历史无业务写入；恢复旧方案必须经过当前基线、原文及身份影响校验，保存为新版本。
6. 迟到结果、切章、刷新服务端状态、并发修改及响应丢失不静默覆盖草稿，不产生重复版本。
7. 既有设计、计划、素材、粗剪和引用保持原身份；划分版本不表达完整生产状态回滚。

不包含：章节正文版本管理、全制作流程版本系统、跨设备草稿同步、版本分支／合并、自动迁移成果、批量删历史、跨章节统计和无关页面重构。

## 3. 版本与记录的统一语义

### 3.1 记录分类

| 对象 | 展示方式 | 可执行动作 | 是否改变当前划分 |
| --- | --- | --- | --- |
| 排队／运行中的分析 | AI 分析 · 等待执行／分析中 | 查看进度、取消任务 | 否 |
| 失败／取消的分析 | AI 分析 · 失败／已取消 | 展开原因；用户重新点击 AI智能划分发起新任务 | 否 |
| 成功但未保存的结果 | AI 方案 · 待保存 | 展开结果、载入编辑 | 否 |
| 保存成功的划分 | v1、v2…；来源为手动／AI／历史恢复 | 查看版本、基于此版本编辑 | 保存时设为当前 |
| 当前版本 | 版本号加“当前”标记 | 编辑当前划分 | 编辑本地草稿不改变正式数据 |

- 正式版本号只在有实际变化且保存成功后产生；无变化保存、预览、分析成功和失败重试均不占用版本号。
- 每个保存版本不可原地改写。一个 AI 任务可关联多个后续保存版本，记录真实来源，不强制一任务一版本。
- 已保存版本与原分析用 `source_task_id` 建立显式关系。表格可在保存版本展开区查看原始 AI 输出；已关联的分析避免作为另一条“待保存”记录重复出现。关联多个版本时保留全部版本。
- “当前划分版本”“正在查看的版本”“未保存草稿”分别表达。历史浏览或本地选择不得改写当前版本指向。
- 页面不再使用笼统的“过期”。按实际原因展示“基于旧原文”“分析后划分已变化”“历史资料不完整”。
- 章节原文改变时，当前划分版本仍保留原快照并标记需核对；不伪造一次划分保存，也不把旧范围绘制到新正文。

### 3.2 查看与恢复

- **查看版本**：关闭历史 Modal，在同一布局中只读展示该版本及当时原文，清楚标明“正在查看 vN／当前 vM”。提供“返回当前编辑”和“基于此版本编辑”的上下文操作，不新增常驻顶部按钮。
- 当前有未保存草稿时，只读查看保留草稿，返回后恢复原输入；关闭整个划场页面仍受草稿保护。只有载入方案并替换草稿时才确认放弃输入。
- **基于此版本编辑**：以当前正式划分作为提交基线，以所选历史版本作为内容来源。恢复 v1 后保存生成 v4 等新版本，不倒退版本号、不修改 v1。
- 原文一致时可复用已验证的范围；原文不一致时先展示旧原文，再以当前原文重新定位。不能把旧偏移直接套用，也不能回写章节原文。历史资料缺失的条目仅供查看。
- 历史快照中的场次 ID 是明确的身份依据。仍在当前划分中的 ID 保留；已经退出的 ID 仅在“恢复方案”的受控提交中允许重新加入，预览明确列出恢复与退出对象。
- 恢复原 ID 必须校验项目／章节归属、该对象当前版本及引用状态；普通历史场次仍禁止生产写入。恢复不倒退对象并发版本，不复制或回滚其设计、素材、采用及接缝记录。
- 新 AI 方案没有历史快照身份依据，不能凭标题或相似范围自动决定复用身份；在统一编辑器内核对映射，保存前确认拆分／合并／退出影响。

## 4. 页面布局

### 4.1 主编辑区

| 区域 | 内容与操作 |
| --- | --- |
| 顶部左侧 | 章节名称、当前版本、草稿／历史浏览状态 |
| 顶部右侧 | AI智能划分、历史版本 |
| 左栏 | 本章场次列表、选中状态、待定位提示；新增场次放在列表内 |
| 中栏 | 完整原文、全部范围、共享边界和选区；继续支持鼠标、键盘及触屏 |
| 右栏 | 当前场次名称、摘录／范围、顺序及身份映射；移出操作放在对应场次内 |
| 底部 | 当前草稿状态、未分配原文提示、放弃修改、保存新版本 |

- 复用现有手动编辑组件与选区算法；AI 只改变草稿来源，不再维护第二套候选编辑界面。
- 点击“保存新版本”先打开现有影响预览 Modal，确认后执行一次事务保存。新增、改名、边界、排序、退出／恢复及成果影响须可核对。
- 保存成功后自动显示新当前版本，保留仍有效的选中场次及阅读位置，不关闭划场页面。
- 明确范围编辑入口继续定位指定场次；旧 `panel=source`、`mode=manual` 等入口能进入同一编辑器，不恢复模式开关。
- 1440／1024px 使用三栏；768／375px 按空间切换列表、原文和选区。顶部两个按钮、底部保存及取消操作可达，不产生整页横向滚动。
- 标题栏关闭始终返回章节表格；保留焦点、页码、搜索和浏览位置恢复，不增加第二个章节组合入口。

### 4.2 历史版本 Modal

表格列：展开按钮、版本／记录、来源、创建时间、场次数、状态、操作。默认按时间倒序，当前版本有明确标记；列表分页，不一次读取所有任务结果和原文。

展开内容：

- 成功方案／保存版本：按顺序展示场次名称、原文摘录、范围及定位问题；保存版本同时展示真实身份和来源版本。
- AI 来源版本：可核对原始分析与最终保存方案，避免把用户调整后的结果误说成 AI 原始输出。
- 运行记录：展示真实进度及取消操作；失败记录展示可处理原因；没有结果时不渲染空的“版本内容”。
- 原文或集合不匹配：展示具体原因；可查看旧内容，载入编辑时进入重新核对流程。

交互约束：打开／关闭 Modal、翻页、展开行和切换查看均不分析、不保存、不改变当前版本。列表和展开详情分别提供加载、失败、重试及空状态。窄屏隐藏次要列、在展开区补齐信息，不删掉版本状态与操作。

## 5. AI 分析与回填流程

1. 点击“AI智能划分”时冻结当前章节、原文版本、当前划分版本／完整成员基线及本地草稿变更标记，明确本次任务身份。
2. 已有未保存修改时，在发起前说明成功后将替换草稿；用户可取消。保存中的页面禁止再次提交分析。
3. 分析中按钮显示“划分中…”并禁用重复提交；页面保留可见的状态提示，历史 Modal 可查看详情和取消任务。允许继续手动编辑。
4. 本次任务成功，且用户仍在同一章节编辑当前草稿、原文／服务端基线／本地草稿均未变化时，自动回填同一编辑器并标记“AI 生成 · 未保存”。不再要求点击“查看结果”和“采用到草稿”。
5. 重复摘录必须选择具体位置，找不到原文的场次标为待定位；不能以整章范围兜底或静默丢弃失败候选。身份映射在同一编辑器处理。
6. 若分析期间继续编辑、切章、进入历史浏览或基线变化，只将结果保留到历史并提示有新方案；不能覆盖输入或将结果回填到另一章节。重新打开页面也不自动载入过去成功结果。
7. 失败／取消保留原编辑内容；重试是用户明确发起的新任务。任务详情读取失败只重试读取，不能重复受理分析。
8. 回填完成后由用户保存；最终版本记录实际编辑结果及来源任务。AI 生成成功本身不修改正式场次、不确认设计、不触发生产或采用。

## 6. 数据、事务与接口

### 6.1 最小数据能力

在现有场次、任务和整章回执上补充章节级保存版本，不建设通用版本引擎。P1 定稿实际表和字段，至少表达：

| 内容 | 约束 |
| --- | --- |
| 版本 ID、章节、展示序号、创建时间 | ID 稳定，序号在章节内唯一且不因排序／分页变化 |
| 完整快照 | 当时原文及 hash、有序成员、身份、名称、范围、摘录和来源；读取历史不拼接当前可变对象 |
| 来源 | 手动、AI、历史恢复、旧记录导入；精确任务 ID、来源历史版本及保存时基线按实际记录，可为空但不得猜测 |
| 身份去向 | 保存实际保留、新增、退出和恢复映射；不能只留不可逆的请求 hash |
| 当前版本指向 | 与实际当前成员集合一致；与新快照、成员更新、回执在同一事务提交 |
| 幂等关联 | 同一请求只创建一个版本，原回执能返回同一版本 ID 和编号 |

`Sequence.version` 继续用于并发控制，`DirectingRevision` 继续表示既有设计／计划／剪辑版本。章节划分版本不冒充这些对象的总版本。

### 6.2 写入与恢复约束

- 复用章节锁和完整成员基线；必要时增加预期当前划分版本、待恢复历史对象版本，防止预览后并发新增、退出、修改或恢复。
- 一次事务完成最终范围验证、影响确认、实际变化成员更新、新版本快照、当前指向和幂等回执。任一后续写入失败时全部回滚。
- 不为未变化场次递增对象版本；恢复历史 ID 使用其当前对象版本继续递增，不写回历史版本号。
- 退出及恢复涉及任务、采用或跨场引用时给出具体影响／阻塞；不静默取消任务、删成果或重写引用。已有任务交付仍归原身份。
- 名称／排序等单场修改入口也必须在同一事务记录整章快照。复用版本记录步骤，不在保存后补写，也不为满足整章范围校验而改变现有“只改名不重新确认来源”的语义。
- 旧 AI 结果不得仅改写 `source_version` 或清空来源任务后绕过校验。历史载入需明确记录原始来源与当前核对基线；未经重新定位和身份核对的旧结果不能保存。
- 响应丢失沿用原请求查回执或重试，不能另起请求创建重复版本；恢复后若其他用户已保存更新版本，应同时表明“本次保存成功”与“当前已更新”，不把旧回执误当最新版本。

### 6.3 查询与 API

- 增加章节范围内的历史摘要分页、版本／分析方案详情，以及历史载入所需的快照和核对信息；具体路径与 DTO 在 P1 定稿。
- 复用真实 Task 记录汇总分析状态。仅轮询本章进行中的任务，避免加载每页历史时对全部任务发起逐项请求。
- 当前章节读取和保存响应提供当前版本身份；提交回执补齐版本身份。对旧回执保持可恢复性，不因新增必填字段导致旧记录无法读取。
- 历史详情仅返回所需的原文、分析结果和版本元数据，不直接暴露完整任务输入快照、供应商凭据或原始响应。
- `api` 层只收参、鉴权和组织响应；业务规则在 service，DTO 在 `app/core/contracts`，前端统一使用 generated client。
- 接口变更后确认 `127.0.0.1:8000` 加载当前工作区，再从项目根运行 `pnpm --dir front run openapi:update`。

## 7. 旧数据接入与迁移

| 旧数据 | 接入方式 |
| --- | --- |
| 原文快照及结果完整的成功分析 | 直接作为历史方案记录展示；没有保存关系时标明“保存关系未知”，不能断言从未使用 |
| 有完整 `DivisionCommit.response` 的保存 | 可导入保存快照；关联原 request_id，稳定去重；缺失任务来源／映射明确为空，不按标题或时间猜测 |
| 只有当前场次、没有完整历史快照 | 记录“接入时当前划分”基线，保留真实身份及来源状态；不补造过去每一次保存 |
| 资料不完整的旧任务／回执 | 保留可验证的摘要与缺失说明，禁止声称可以完整恢复 |

- 必须基于实际数据库盘点决定回填范围，不能从当前代码存在回执表推断业务库已经有这些记录。
- 当前基线取实际成员状态，不直接用时间最新的旧回执代替；单场改名、排序可能发生在该回执之后。无法匹配时建立明确的接入基线。
- 导入顺序稳定，时间相同使用稳定身份辅助排序；缺少可证实先后关系时不把导入顺序宣称为原业务保存顺序。
- 回填可重复运行且不重复创建版本；不删除任务、场次、成果或原回执。无场次且无保存历史的新章节显示“尚未保存”，不因打开页面创建版本。
