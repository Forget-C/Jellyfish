# 五类交互会话的轮次、受理回执与恢复

Status: ready-for-agent

Completion: resolved

Integration branch: codex-unified-chat-integration

Validated revision: eef4cb6b

## Problem Statement

用户在画布助手与实验室里都能发送消息，但断流、停止和重开页面时，能否继续输入、先前的问题是否还要回答、生成任务是否仍在运行，取决于各页面如何拼接回执、事件和历史。一轮对话可能连续追问两次。若重传第一次答案拿到了第二次答案的游标，用户就会错过一段记录。若页面把迟到的旧轮次结果当作当前输入的结果，用户正在编辑的下一条消息也可能丢失。

## Solution

页面打开时绑定一次交互会话，之后通过同一个聊天客户端发送、订阅和恢复。服务端受理命令后立即返回回执，执行过程和结果由 SSE 交付。重新打开时先读历史快照，再补读快照之后的事件。用户主动发送“继续”会开启新轮次，由模型结合已有聊天历史理解正文。用户点击问题卡回答时，答案接续原轮次，并取得属于这次回答的回执。

## User Stories

1. 作为画布或实验室用户，我希望打开会话后始终向已选会话发送，以便切换页面时消息仍归属于正确的会话。
2. 作为聊天用户，我希望提交后立即知道本轮已受理，以便模型尚未输出时也能停止回复。
3. 作为聊天用户，我希望逐步看到正文、工具调用、追问、任务和结果，以便了解本轮做到哪一步。
4. 作为暂时断线的用户，我希望继续编辑下一条正文和附件，以便连接恢复后接着工作。
5. 作为正在编辑的用户，我希望旧轮次完成后保留新草稿，即使它与刚才发送的文字相同。
6. 作为没有收到回执的用户，我希望页面核实原请求，以便安全重试且只产生一份消息、一次执行。
7. 作为重新打开会话的用户，我希望找回服务端已受理的轮次，即使关闭时尚未收到回执。
8. 作为离开会话的用户，我希望后台继续工作，并由我明确决定何时停止回复。
9. 作为回答连续追问的用户，我希望每个答案都关联原问题，以便刷新或网络重传后仍能看到正确的待办。
10. 作为继续讨论的用户，我希望发送“继续”与其他正文一样进入历史，以便模型依据已有讨论开始新一轮分析。
11. 作为画布用户，我希望重开后在原轮次查看提案、版本、分组审批与执行结果，以便安全处理待办。
12. 作为多模态聊天用户，我希望回复结束后立即开始下一轮，同时继续查看已受理的图片或视频任务。
13. 作为文本试模用户，我希望恢复部分回复并能辨认终态尚待核实的运行，以便判断是否需要继续等待。
14. 作为图片或视频试模用户，我希望恢复原任务、素材和参数，以便查看产物或回填后发起一次新生成。
15. 作为查看较早消息的用户，我希望翻页时仍能接收当前会话的新事件，以便兼顾历史和进度。

## Implementation Decisions

### 一次定位会话，三项公共操作

五类会话为画布助手、实验室多模态聊天、文本试模、图片试模、视频试模。同一基础客户端用服务端给出的 kind 和 session_id 绑定会话；仅有 ID 的深链接在打开时解析一次类型。后端核实 kind 与持久化会话一致，再分派给场景实现。前端页面和后端场景逻辑都可以保留必要包装。

| 操作 | 相对 /api/v1/studio/chat/sessions/{kind}/{session_id} 的路径 | 公开行为 |
| --- | --- | --- |
| send | POST /turns | 校验、持久化受理后返回 HTTP 202，回执字段为 session_id、turn_id、cursor。模型执行与任务完成独立于 HTTP 响应。 |
| events | GET /events?after=… | 按会话游标发送已提交的公共 SSE 事件，随后持续监听。事件类型和有类型的载荷表达正文、工具、追问、任务、产物和轮次终态。 |
| snapshot | GET /snapshot | 返回会话身份、类型、历史记录、当前可核实的轮次状态、适用操作和快照游标。场景详情按 kind 区分。首次打开仅需绑定好的会话，翻阅较早历史时才需分页参数。 |

支持问题卡的两类聊天通过原轮次的续答操作提交答案，同样返回 202；后续输出使用该会话的 events。未保存画布首次调用助手时先自动保存，以持久化会话完成受理和恢复。

### 历史、回执和游标

快照给出某个会话游标时的历史与当前待办，包含稳定的展示身份和顺序。客户端从该游标补读其后已提交的事件，覆盖快照读取与订阅建立之间的时间窗口。区分三个用途：

- 命令回执的 cursor 是该次命令固定的回放起点。使用排他参数 after 从这里订阅，可读到该次受理及后续事件；订阅覆盖整个会话。
- 会话已处理游标标记当前页面已应用到哪里。应用较新快照或成功处理事件后再推进；重复事件去重，迟到快照或旧命令回执不得倒退当前状态。
- 历史分页位置只定位较早的记录。向上翻页保持实时订阅的进度。

| 会话 | 快照与展示须保留的差异 |
| --- | --- |
| 画布助手 | 按轮次保留选区与引用依据、提案和版本、分组审批、冲突、执行结果、当前问题和进度。审批仍绑定原提案和决定。 |
| 实验室多模态聊天 | 保留消息、部分回复、当前追问、主模型及媒体模型选择、工具与产物的关系。工具错误的实时消息与历史消息可按同一身份合并。 |
| 文本试模 | 保留逐轮独立输入、模型、部分正文、已核实终态；断流后允许表达终态未知。 |
| 图片试模 | 保留参考图、可回填参数、任务回执、进度、错误与归档图片。 |
| 视频试模 | 复用媒体任务回执，另保留首尾帧、主体参考、时长、分辨率等本轮实际输入及归档视频。 |

### 普通发送、续答和重传

服务端先按命令身份查已受理记录，再判断当前是否忙碌、当前问题能否接受新答案。首次接受时，在同一事务内关联命令身份、受理时的输入与受理事件，使回执能够稳定找回。并发重传只取得一次执行业务的资格。既有受理事件与消息记录可继续作为依据。

| 操作 | 识别和执行规则 |
| --- | --- |
| 普通发送 | 由会话与客户端请求身份识别。每次主动发送使用新请求身份，受理后开启新 turn_id；同一身份和原始输入返回完整原回执。同一身份携带不同正文、附件引用或显式参数返回 409。客户端以原输入重传，服务端沿用受理时的选择。 |
| 问题卡续答 | 由会话、turn_id 和 question_id 识别。每个具体追问有独立身份且只接受一个答案。首次有效答案沿用原 turn_id，登记独立回执；同答案重传返回该答案原回执，即使已进入下一次追问、本轮已停止或已结束。更改已接受的答案返回 409。 |
| 主动发送“继续” | 遵循普通发送规则，作为一条新消息写入历史，由模型结合历史理解其含义。原轮次保留其终态。活动轮次的普通发送限制仍适用；待回答的问题通过问题卡处理。 |

例如，同轮原发送、第一次续答、第二次续答的受理事件游标分别为 41、46、52，回执起点分别为 40、45、51。网络重传其中任何一项，只返回对应原回执；不会再次执行模型、生成任务或写入用户消息。交互轮次、请求身份、后台任务和文件各有用途。继续支持历史数据已有的回执定位规则，包括缺少独立续答受理事件的画布记录、已知终态的旧文本运行和旧媒体受理载荷。

### 前端轮次状态归属

服务端持有业务事实。统一客户端按绑定会话跟踪提交中的原命令、回执、连接状态、已处理游标、活动轮次、可停止目标和当前待办。画布助手与多模态聊天各通过一条会话订阅处理发送及续答结果。首帧先于回执到达时按轮次关联；迟到回执不得重新激活已结束轮次。历史问题仍可出现在事件记录中，页面只为当前待回答的问题显示可操作卡片。

页面拥有可编辑草稿的版本、附件、上传、选区、回填和卡片交互。客户端按命令身份报告结果，页面只清理或恢复当时提交的草稿版本。后续编辑的正文和附件，即使值与原稿相同，也应保留。模态特有的发送限制由对应页面结合公共状态处理。

- **停止**　聊天收到 202 后即能按 turn_id 请求停止。服务端确认该轮停止或已结束后立即解除轮次占用，挂起的 SSE 或待办核实请求不可继续锁住输入。停止结果未知时先核实。已受理的媒体任务继续跟踪，取消任务由任务卡独立处理。
- **断线**　保留最后已知轮次与部分输出，允许编辑草稿。确认上一轮结束后才开放下一条普通发送；若确认原请求已被拒绝，解除该请求的提交限制。重连后按已处理游标补读，必要时读取快照核实。
- **页面仍打开，未收到 202**　客户端保有请求 ID、原始正文、附件引用和参数。先核实原请求，需要重传时沿用同一身份及输入。其间可编辑下一条草稿。
- **关闭或离开**　画布面板关闭、离开实验室会话时释放页面订阅，只在用户显式点击停止时请求停止执行。重新打开先读服务端快照，再接 SSE。找回已受理的进行中或已结束轮次；服务端未受理的命令不因重开而自动补发。若原请求在快照之后才受理，后续 SSE 补上该事件。

## Testing Decisions

1. **五类会话的公开 HTTP 与 SSE。** 使用可控的慢模型或任务执行器，经真实会话分派、持久化和事件读取，验证类型匹配、业务尚未完成时已返回 202、统一事件载荷和各场景历史详情。覆盖订阅前已有事件、快照与订阅之间的新事件、历史分页期间的新事件，以及断线后续读。沿用现有统一路由、历史迁移和媒体任务回执用例。
2. **两类聊天的命令回执。** 从同一公开入口发送并连续回答两个问题，逐项重传，比较整个回执及 SSE 起点，计数模型调用与任务提交。覆盖并发相同命令、相同身份不同输入、停止后重传答案、已回答的追问回放和历史兼容。主动发两次“继续”得到两个新轮次，自动重传其中一次仍是原轮次。
3. **真实页面与统一客户端。** 复用画布助手和多模态实验室浏览器流程。控制回执、事件、快照的到达顺序，验证首帧挂起时停止后立即发送；回执迟到时保持终态；断线时草稿 B 的正文与附件可编辑，A 的结果不能清理 B；迟到事件不能重开已回答的问题。验证关闭只断开订阅，重开恢复已受理轮次，对未受理请求不自动补发。模拟页面仍打开但 202 丢失，核对重传的请求身份和输入。通过用户可见状态、实际请求及回执验收。

## Out of Scope

供应商协议、模型能力声明、工具执行框架的重构；改变画布审批授权或后台任务取消规则；新增“继续这轮”按钮；统一尚未提交草稿的跨刷新保存策略。

## Further Notes

本规格承接已完成的统一聊天工作。ADR 0017 的交互会话协议与 ADR 0021 的聊天、试模分工继续适用。实现可复用当前工作树中关于稳定回执、短事务、停止及工具失败消息的修复。公开契约变更同步更新 OpenAPI、生成客户端和使用文档。
