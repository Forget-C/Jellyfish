# 共享 graph 契约与单元画布改造

Status: ready-for-agent

日期：2026-10-21

本规格由已确认的讨论和实施计划整理，沿用既有决策、测试边界及 A01–A20 验收标准，不新增待确认事项。状态表示需求可进入任务拆分和实现，不表示功能已经落地或验收通过。

## Problem Statement

当前单元画布围绕镜头依据、单元设置和参考素材组织展示，用户难以像使用导演画布一样，在全部镜头、某个镜头和单元详情之间连续浏览。配置集中在单元设置内，缺少可快速识别内容与缺项的摘要卡，也难以直接理解一个单元如何执行六岗设计。

镜头与生产单元不是一对一关系。同一镜头可以有多个单元；现有存储也允许一个单元有多个覆盖项，包括跨镜头覆盖。若把镜头选择放入依据卡、把某个镜头当作单元唯一父级，或按筛选结果复制单元，会误表达业务身份和执行范围。

导演与单元画布尚未共用完整的后端展示图契约。前端仍需从业务内容构造节点、成员、摘要或关系；仅复用画布外观组件，会使每个新画布继续重复数据组装、引用校验、导航与布局状态处理。展示与真实业务含义也可能逐渐偏离。

工作台已经具备本地恢复、手动保存、自动保存、请求幂等和 revision 并发保护，但当前自动保存调度与失败后的处理不满足已确认的周期重试要求。新的后端 graph 与用户正在编辑的内容还必须保持清晰边界：迟到的保存响应或旧图载荷不得覆盖更新的输入；保存失败不能导致数据丢失，也不能把旧准备状态当作当前输入已核验。

## Solution

将单元画布组织为“镜头依据 → 单元聚合入口 ← 参考素材”。左上角使用悬浮的返回、前进、面包屑和全部／指定镜头切换；点击单元进入独立子图，查看动作覆盖、生成配置、组织要求、前段依赖四类摘要卡，并在详情中继续编辑。参考集合和只读的本单元执行依据在相关位置可达。

导演与单元画布使用相同的基础 graph 协议，后端提供完整的业务展示内容、关系和视图。两类图拥有各自强类型业务载荷及投影器，共用图构建、身份与引用规则、完整性校验和契约测试。前端共用图容器、导航、聚合预览及布局状态，只负责渲染、交互和几何处理，不重新拼装业务图。

四个画布继续共用现有工作台保存机制，默认每 5 秒检查未保存编辑数据，手动保存和自动保存进入同一串行队列。暂时性失败保留输入并允许下周期或手动重试；结果未知时核验或原样重放原请求；revision 冲突沿用显式处理。关闭页面后的恢复仍使用现有本地持久化，不引入领域草稿、第二套保存系统或额外发布阶段。

本轮迁移导演和单元 graph；指令与剪辑画布仅承接共同保存机制修正。现有六岗、编译审稿、能力检查、试拍、素材审查和剪辑采用的业务职责保持不变。

## User Stories

1. 作为准备拍摄的用户，我希望默认浏览全部镜头及相关单元，以便快速了解本场生产准备情况。
2. 作为用户，我希望在悬浮导航中切换全部镜头或指定镜头，以便聚焦当前工作而不改变单元本身。
3. 作为用户，我希望镜头依据卡展示真实设计依据，以便理解单元的来源。
4. 作为用户，我希望看到一个镜头关联的多个单元，以便组织分段拍摄或局部补拍。
5. 作为用户，我希望同一个跨镜头单元在不同筛选下保持相同身份，以便不会误认为存在多个生产工作副本。
6. 作为用户，我希望点击单元聚合入口进入独立子图，以便集中查看该单元的配置与参考。
7. 作为用户，我希望单元子图展示全部覆盖项和依据，以便入口镜头不会缩小我理解的单元范围。
8. 作为用户，我希望面包屑表达“单元画布 › 单元”，以便不会把某个镜头误认为单元唯一父级。
9. 作为用户，我希望返回或前进时恢复此前筛选、视口和缩放，以便连续浏览时不必重新定位。
10. 作为从导演镜头进入的用户，我希望打开该镜头的单元视图，以便直接衔接设计与生产准备。
11. 作为重新进入画布的用户，我希望恢复当前版本上次筛选，以便继续此前的工作。
12. 作为从任务或精确链接进入的用户，我希望直接定位对应单元，以便查阅真实业务对象而非猜测第一个镜头。
13. 作为用户，我希望目标删除或不可访问时得到明确说明，以便系统不会用同名或其他对象替代。
14. 作为用户，我希望全部镜头视图下新增或 AI 设计单元前明确目标镜头，以便操作范围可控。
15. 作为用户，我希望单镜头视图的新增操作使用当前镜头，以便减少重复选择。
16. 作为用户，我希望动作覆盖卡逐项显示镜头、动作范围和执行选择，以便多覆盖项不会被隐藏。
17. 作为用户，我希望生成配置卡展示模型、时长、画幅、种子及其他参数，以便快速检查拍摄设置。
18. 作为用户，我希望组织要求卡展示入幅、出幅和待准备参考，以便知道单元如何衔接及尚缺什么。
19. 作为用户，我希望前段依赖卡显示固定来源、实际落幅与复核状态，以便不会把计划衔接当作已验证的素材衔接。
20. 作为用户，我希望卡面展示摘要和问题、详情负责编辑，以便既能浏览全貌又能继续使用熟悉的编辑方式。
21. 作为用户，我希望每个单元有可在总览和子图访问的参考集合，以便快速查看缩略图、数量和绑定问题。
22. 作为用户，我希望同一文件在不同单元中的用途、输入角色和顺序独立保留，以便调整一处参考不会改变另一处输入。
23. 作为用户，我希望待准备参考要求与已经绑定的素材分别显示，以便不会把准备要求误认为模型已经收到的输入。
24. 作为用户，我希望查看本单元执行、约束、背景和未解决项及其来源，以便理解六岗设计如何进入本次工作。
25. 作为局部拍摄用户，我希望完整镜头描述不会自动扩大本次动作范围，以便只执行当前单元明确选择的内容。
26. 作为用户，我希望声音与后期内容按相应阶段解释，以便不会把所有设计内容都当作本次视频生成要求。
27. 作为用户，我希望多覆盖项单元可以保留和编辑，同时明确当前执行限制，以便不会因展示完整就误判为可直接生成。
28. 作为用户，我希望查看固定历史依据时保留原始身份，以便当前对象调整不会改写历史记录。
29. 作为用户，我希望素材缺失、模型能力未知或前段待复核时看到真实状态，以便旧图不会给出错误的可执行结论。
30. 作为用户，我希望导演和单元画布采用一致的导航、聚合入口和布局操作，以便无需学习两套交互。
31. 作为用户，我希望聚合预览与进入后的子图表示相同成员，以便预览能够帮助判断内容而不改变浏览状态。
32. 作为用户，我希望保存后稳定节点保留手动位置，以便内容保存不会打乱我的工作布局。
33. 作为用户，我希望连续输入时也按固定周期保存，以便不必停下编辑才能获得保存保护。
34. 作为用户，我希望手动保存与自动保存协调执行，以便重复操作不会造成并发覆盖。
35. 作为用户，我希望保存过程中能够继续编辑且新输入始终保留，以便迟到响应不会撤回我的修改。
36. 作为用户，我希望图尚未同步时得到明确提示，以便不会把旧摘要当作最新编辑结果。
37. 作为用户，我希望新增单元保存失败后仍可重新打开详情继续修改，以便无需先保存成功或寻找额外草稿工作区。
38. 作为用户，我希望网络失败后看到提示并可手动或等待下周期重试，以便不丢失输入且无需重新录入。
39. 作为用户，我希望结果未知的请求先被核验，以便重复提交不会把新内容混入旧请求或重复业务动作。
40. 作为用户，我希望字段校验错误准确定位并在修正后再保存，以便系统不会不断重发同一非法内容。
41. 作为用户，我希望服务端版本已更新时显式处理冲突，以便旧本地内容不会覆盖别处的新修改。
42. 作为用户，我希望关闭页面后恢复未保存编辑数据与必要的请求状态，以便中断工作不会丢失输入。
43. 作为用户，我希望恢复前先核对服务端且保护其他未处理恢复记录，以便恢复操作本身不会造成覆盖。
44. 作为用户，我希望在四个画布之间切换时得到相同的保存和恢复保护，以便不需要记住不同页面的规则。
45. 作为用户，我希望 graph 加载失败或浏览器存储不可用时看到准确提示，以便系统不会虚报内容已保存或准备完成。
46. 作为用户，我希望从配置和参考准备继续完成编译审稿、检查、试拍及 Take 回看，以便画布调整后仍能完成原有流程。
47. 作为审片用户，我希望生成成功、素材审查、实际覆盖和剪辑采用分别表达，以便新画布不会自动替我采用结果。
48. 作为前端维护者，我希望获得可直接呈现的强类型业务图，以便不为每个画布重复数据拼接和状态推断。
49. 作为后端维护者，我希望两个投影器共用身份、构建、引用校验和一致性测试，以便后续维护有明确标准可依。
50. 作为维护者，我希望共同图组件与业务渲染、布局规则和编辑命令有清晰边界，以便复用不会演变为通用动态表单或隐藏业务规则。

## Implementation Decisions

### 1. 范围和领域不变量

- 导演和单元画布迁移到共同 graph 协议及公共图形能力；指令、剪辑画布本轮不迁移 graph。共同保存、重试和恢复的行为修正覆盖四个画布。
- 场次版本是一套持续编辑的完整方案；保存延续同一版本并推进 revision。未保存编辑数据不是另一份场次版本，不新增草稿、发布或确认阶段。
- 当前场次版本中的生产单元保持既有版本身份与 `unit_id` 关联；固定历史来源继续保留其原有生产计划版本等身份。筛选、视图引用或展示节点不得创建另一份生产单元。
- 现有存储支持一镜多单元和一单元多覆盖项，覆盖项可以指向不同镜头。当前 AI 单元组织、指令和视频准备仍要求恰好一个 coverage 项；同镜头两个覆盖项也受限制。
- 六岗仍为 `direction`、`performance`、`staging`、`cinematography`、`continuity`、`prompt`。导演负责设计，单元负责组织既定设计的执行；声音是内容和制作阶段，不新增岗位。
- 继续使用已有 `unit_scope`／`resolved_design_fields` 表达执行范围。可见节点、连线、共享对象、筛选结果不能成为新的执行范围来源；完整镜头 `visible_result` 不自动要求每个局部单元完整执行。
- 设计完整性、拍摄准备完整性、图结构完整性、运行任务、素材审查、实际覆盖和剪辑采用分别表达。图结构校验通过不构成业务执行授权。
- 既有固定来源和历史生成记录保持不可变；当前对象调整不能重新绑定历史。当前可编辑内容的保存遵循既有版本规则，不扩大历史编辑权限。

### 2. 浏览、入口和精确定位

| 情境 | 已确认行为 |
| --- | --- |
| 悬浮导航 | 返回、前进、面包屑及全部／指定镜头切换；筛选器不放入镜头依据卡 |
| 总览 | 镜头依据、单元聚合入口、每单元参考集合；素材输入边指向单元 |
| 单元入口 | 点击进入独立子图，面包屑为“单元画布 › 单元 07”；不在总览原地展开 |
| 单元子图 | 展示完整单元依据和覆盖项，不因入口镜头裁剪；返回恢复原筛选、视口及缩放 |
| 从导演镜头进入 | 打开该镜头的单元浏览视图 |
| 正常进入 | 恢复当前版本上次筛选；首次进入全部镜头 |
| 精确链接或任务回跳 | 直接定位单元身份，展示完整依据与固定来源 |
| 全部镜头下新增或 AI 设计 | 明确选择一个目标镜头，再调用既有操作 |
| 单镜头下新增 | 使用当前镜头；修改已有单元按精确单元身份定位 |
| 目标失效 | 明确提示删除或不可访问，不按同名、数组顺序或第一个覆盖项替代 |

### 3. 配置、参考与六岗执行依据

| 类别 | 内容与职责 |
| --- | --- |
| 动作覆盖 | 逐覆盖项展示镜头、动作范围、显式执行选择；保留子项身份 |
| 生成配置 | 模型、时长、画幅、种子及额外参数；沿用既有能力与字段校验 |
| 组织要求 | 入幅、出幅和待准备参考要求；组织来源与理由放在详情 |
| 前段依赖 | 固定来源、实际帧／落幅、绑定与复核状态；复用依赖编辑行为 |

卡面展示摘要和缺项，详情更新当前编辑内容，应用／取消沿用既有编辑边界和保存方式。四类配置不机械映射为六张岗位卡。

每个单元有一个参考集合卡，总览提供缩略图、数量和问题，子图仍可查看和编辑同一集合。相同文件在不同单元中的绑定保持各自身份、用途、输入角色和顺序。待准备要求不等于实际绑定，绑定不等于模型已接受输入。

只读“本单元执行依据”通过现有详情入口访问，消费后端已有范围解析结果，明确执行、约束、背景和未解决项，区分视频、声音、后期阶段并可定位来源字段。生成准备、编译审稿、能力检查和试拍继续调用原业务服务，不从图推断授权。

### 4. 共同 graph 协议

| 部分 | 必须表达的语义 |
| --- | --- |
| 图身份 | 图种类、版本身份、整数 revision；与响应业务内容属于同一快照 |
| 节点 | 稳定 ID、区分式节点种类、业务对象引用、展示载荷、来源及编辑目标 |
| 边 | 稳定 ID、端点、关系种类及真实覆盖项／绑定／字段证据；区别业务关系与布局引导线 |
| 视图 | 身份、成员、可见边、锚点、进入目标、层级及普通卡／聚合入口／只读引用等呈现角色 |
| 问题 | 共用 `code`、`message`、`severity`、`target`；保留领域含义，不压成通用“完整”状态 |

导演和单元采用同一基础协议，但分别拥有强类型业务载荷；不使用任意数据袋。标题、编号、名称、摘要、计数、成员、缺项、明确适用范围和业务准备状态由后端提供。仅返回 ID 或路径，让前端再次关联原始业务数组，不满足本规格。

业务对象身份与展示位置分离。同一对象可以被不同视图引用；覆盖项和参考绑定的编辑目标必须精确，路径只承担辅助定位，不靠标题或数组顺序推断长期身份。

历史无稳定 ID 项显式标为 `stable=false`，目标仅在相应 revision 内有效；不在读取时写入新 UUID，不跨 revision 重用临时目标。固定历史来源携带自己的版本上下文，不与当前图版本混淆。

导演既有 `placement`、`uses`、`applicability`、`paths` 保留其领域语义，不强迫单元配置使用这些结构。迁移同时检查已有关系图的详情、来源和检查消费者，避免留下另一套前端业务推断。具体响应字段和类名按现有消费者收敛，属于实现选择。

### 5. 后端复用和分层标准

- 契约模块定义基础 DTO、区分式业务载荷、身份、引用、目标和纯数据约束；不执行数据库查询或业务编排。
- 共同读取上下文固定内容与 revision，并复用或批量加载来源、素材及能力证据；权限和证据有效性继续由既有领域服务负责。
- 共同图构建工具负责节点／边／视图／问题注册、索引、冲突检测和最终完整性校验。少量函数或小型构建器即可，不预设继承体系、插件或反射路径引擎；工具自身不做 I/O 或鉴权。
- 导演和单元投影器负责各自的范围、成员、筛选视图、摘要、来源及状态，复用既有业务校验和共同图工具，不能各写一套基础注册与校验。
- API 负责收参、鉴权、调用服务和响应组织；业务图编排放在 service 层。只移动本次相关的契约模块内业务构建，不顺带搬迁无关内容。

两个投影器必须通过同一组共同完整性规则：

1. 节点、边和视图 ID 唯一，重复定义冲突可定位。
2. 边端点、视图成员及视图引用边闭合；可见边的两端在相应视图中可定位。
3. 业务对象引用一致，视图父级无环，聚合入口指向有效子图。
4. 锚点、来源、问题和编辑目标有效；外部或历史目标显式带上下文，不当成本图成员误验。
5. 内容、图和当前目标的版本／revision 一致，历史来源版本单独表达。

缺失业务引用显式表示缺失状态或问题，不静默删边伪造完整；构造出的非法图结构由共同校验拒绝。结构通过不替代权限、文件、模型或执行范围检查。

### 6. 服务端快照与证据时效

现有场次版本读取和保存响应提供导演与单元两类 graph。内容和图使用相同版本及 revision；graph 是派生结果，不单独持久化为第二份业务事实，不接受前端上传节点与边作为业务写入。

前端 API 调用继续使用 OpenAPI generated client。对外契约变化同步后端、OpenAPI 及 generated client；生成前确认运行中的后端加载当前改动。最终交付不保留旧前端拼图回退路径。

文件、模型能力和前段落幅可能在场次 revision 不变时变化；证据未知、加载失败或待复核时如实展示，最终编译、检查与试拍重新验证实际输入。不得因相同 revision 就保证所有外部证据仍有效。

不新增每次编辑触发的 graph 投影请求。图加载或响应失败提供错误和恢复入口，不回退前端组图，也不因此丢弃当前编辑内容或未知结果的请求证据。

### 7. 前端复用标准

| 能力 | 共同部分 | 业务专属部分 |
| --- | --- | --- |
| 基础画布 | 现有视口、卡片、拖动手柄、边、节点框架及几何能力 | 不承载领域判断 |
| 图容器 | 小地图、聚焦、适配视图、节点与边容器 | 导演分组、标签和 ID 前缀规则留在业务适配层 |
| 导航 | 悬浮返回／前进／面包屑、浏览历史 | 业务跳转命令和详情目标 |
| 聚合入口与预览 | 共用外壳和只读子图预览，消费真实视图成员及后端计数 | 各业务节点渲染 |
| 布局状态 | 手动位置、缓存、重排及撤销 | 导演排布规则、旧布局缓存迁移及单元排布规则 |
| 详情和准备组件 | 复用主题、按钮、详情、正文预览、参考及来源等已有组件 | 原绑定、上传、依赖与历史来源校验 |

节点渲染按强类型种类穷尽分派，不生成任意动态表单。前端可以格式化单位、截断文本、计算坐标和尺寸、管理缩放及导航；业务成员、关系、摘要和准备状态由后端决定。

聚合预览与进入后的子图使用同一成员和布局解释，预览不改写浏览历史或布局缓存。缓存按用户、项目、场次、版本和视图隔离；稳定节点不因保存后的 revision 变化丢失手动位置，无稳定身份项遵守 revision 边界。

### 8. graph 基线与当前编辑内容

工作台分别维护已确认服务端基线和当前编辑内容。graph 对应基线；编辑详情与输入控件读取当前编辑内容。旧图载荷、刷新结果或迟到保存响应不能直接覆盖当前输入。

- 有未保存编辑数据时提示图待同步，旧摘要和准备度不表示当前输入已核验。
- 新增或修改对象继续使用既有编辑／选择入口；保存前、保存失败后及关闭详情后，仍可重新进入当前对象继续编辑。
- 不为显示新对象强制保存，不由前端拼临时业务节点，不增加独立草稿工作区。
- 当前已移除或调整的对象不能从旧图错绑到其他对象；按明确身份核对当前内容，必要时说明目标不可用和图待同步。
- 保存成功后用后端 graph 推进基线；存在更新的输入时仍保持未保存及图待同步状态。

### 9. 周期保存、请求身份和并发

默认每 **5 秒**检查待保存内容，无修改不请求，有修改且无在途保存才提交。持续输入不阻止周期检查。手动与自动保存共用现有串行队列；不增设保存入口、配置页或并行请求。

一次提交固定版本、`expected_revision`、`request_id` 及发送内容。响应核对版本、预期递增的 revision、请求身份、实际提交内容和 graph 一致性后，只更新确认基线，不覆盖请求期间的新输入。

已确认示例：revision 8 提交 A 后用户输入 B，A 返回 revision 9 和 graph A。基线成为 A／9，当前内容仍为 B；下一次以 revision 9 和新请求提交 B。B 不能被 A 覆盖，也不能因 A 成功而被误标为已保存。

### 10. 失败、未知结果和恢复

| 情况 | 行为 |
| --- | --- |
| 暂时性网络失败 | 保留输入和可见错误；支持手动或下周期重试 |
| 结果未知 | 保留原请求身份、预期 revision 和发送内容，先核验或原样重放；不混入后续输入 |
| 原请求确认成功 | 推进基线，后续输入仍待保存，再使用新 revision 和新请求提交 |
| 内容校验失败 | 定位问题，等待修改；不周期重发相同非法内容 |
| revision 冲突 | 沿用显式冲突处理；不盲目重试或自动覆盖服务端 |
| 响应不满足契约 | 不认定已保存，保留输入与请求证据，核验实际结果 |

复用后端现有最近一次保存请求的幂等信息，不将其误当作任意历史请求账本。其他保存已推进版本时，旧请求继续按恢复或冲突规则处理。已有保存并生成操作的未知结果只核验或重放原授权请求，不自动形成新的生成意图。

沿用既有本地持久化，保存确认基线、当前编辑内容、既有撤销／恢复依据及必要的在途请求信息。重新进入先核对最新服务端，再恢复或处理冲突；保护另一尚未处理的恢复记录，不引入无限多版本缓存。布局和图快照不能代替编辑恢复。

服务端未更新不能覆盖可恢复输入，服务端已更新不能被旧本地内容直接覆盖。浏览器存储不可用时明确说明恢复能力受限，不虚报已保存到服务端。

## Testing Decisions

### 已确认的测试边界

沿用既有验收选择，不新增需要用户确认的测试接口。优先通过最高且已有的边界验证行为：

1. **场次版本读取／保存及既有业务 HTTP 接口**：覆盖 graph 内容、身份、快照一致性、revision、请求重放、真实范围和执行限制。复用已有版本读写、多覆盖项保存、单元组织范围及设计完整性测试基础。
2. **真实浏览器操作工作台**：覆盖导航、摘要与详情、参考准备、四画布保存、失败、关闭恢复和冲突。复用现有场次版本工作台、画布导航、单元覆盖／组织和导演布局浏览器用例。
3. **共同图契约公开边界**：让两个投影器运行同一套一致性断言，补充重复 ID、悬空端点、循环视图、无效目标及跨 revision 目标等异常输入。已有几何测试继续验证必要的布局结果。

测试验证可观察结果及契约，不锁定私有函数、内部调用顺序或机械复刻实现。保存测试同时观察用户当前输入、实际持久化内容、请求身份和版本推进；不能只检查成功提示。外部网络失败、响应延迟和并发推进使用受控测试条件，不能通过修改真实业务数据制造故障。

业务范围校验沿用既有服务，不另造测试用领域规则。共同能力确实被两个投影器／画布复用，通过共同契约用例和代码审查共同验收；不依赖一套仅为测试存在的抽象。

### 验收矩阵

保留已确认的 A01–A20 编号，均待实施后验证。

| 编号 | 场景 | 必须满足 |
| --- | --- | --- |
| A01 | 一个镜头多个单元、一个单元跨多个镜头、同镜头多个 coverage 项 | 关系完整、单元不复制；筛选不缩减子图依据；执行限制保持原语义 |
| A02 | 全部镜头／单镜头／单元子图来回切换，使用前进与返回 | 导航层级、筛选、视口和缩放可恢复；聚合预览不改变浏览状态 |
| A03 | 导演进入、常规进入、任务精确回跳、目标删除 | 按入口规则定位；不会以第一覆盖项或同名对象代替目标 |
| A04 | 全部镜头或单镜头下新增／AI 设计单元 | 目标镜头明确；不隐式执行跨镜头或批量生成 |
| A05 | 四类卡片摘要、详情修改、取消、重新进入 | 正确编辑同一单元对应子项；保存入口统一；未保存输入不因旧 graph 被重置 |
| A06 | 同文件被多个单元以不同用途绑定，调整顺序或移除 | 各绑定身份和输入含义保留；待参考要求与已绑定素材不混淆 |
| A07 | 部分动作、共享六岗依据、声音／后期内容 | 执行／约束／背景／未解决项准确；完整镜头描述不扩大单元执行范围 |
| A08 | 无素材、缺来源、模型状态变更、前段采用替换 | 显示具体缺失／未知／待复核；图完整不绕过实际编译和生成校验 |
| A09 | 历史来源、已确认版本、对象已删除、无稳定 ID | 固定记录可读且不改写；临时目标不跨 revision 复用 |
| A10 | 共同 graph 的重复 ID、悬空边、循环层级、无效编辑目标 | 两个投影器共用校验拒绝非法结构，并提供可定位问题 |
| A11 | 持续输入超过一个周期、无修改、重复点保存 | 有修改按周期检查；无修改不请求；自动与手动保存无并发覆盖 |
| A12 | 提交 A 后输入 B，A 的响应迟到 | 基线与 graph 更新到 A，B 保留且仍待保存；下一次保存使用新的 revision |
| A13 | 网络失败及未知结果后继续编辑 | 输入和错误提示保留；下周期或手动原样重试旧请求，成功后再提交新内容 |
| A14 | 校验失败与 revision 冲突 | 非法内容等待修改；冲突显式处理；不无限重试，不静默覆盖 |
| A15 | 关闭页面、重新进入；服务端未变或已推进 | 恢复当前输入与在途证据，先核对服务端；保护另一待处理恢复记录 |
| A16 | 新增单元后保存失败，关闭详情再打开；编辑或移除已在图中的对象 | 当前编辑入口可继续使用；旧图不会错绑目标；不强制保存或前端补造节点 |
| A17 | 保存成功后 graph 更新、手动位置及四个画布间切换 | 稳定节点位置保留；最新输入不被旧响应覆盖；四画布使用同一保存与恢复规则 |
| A18 | graph 加载／响应校验失败、只读历史、存储不可用 | 错误与能力限制真实可见；不前端重建图，不虚报已保存，不丢本地输入 |
| A19 | 既有保存并生成请求结果未知 | 只核验／重放原授权请求，不产生新的生成意图或重复业务动作 |
| A20 | 配置 → 参考 → 编译审稿 → 预检 → 试拍 → Take 回看 | 既有主流程可完成；生成结果不自动采用，实际覆盖与剪辑仍由各自业务处理 |

### 验证完成标准

- 共享后端契约变化运行 directing 相关测试集；影响超出该边界时扩大验证，并执行项目要求的后端静态检查。
- 前端变化执行 TypeScript 检查及相关浏览器回归；共同保存行为必须覆盖四画布及其切换，图改造覆盖导演与单元。
- 对外接口契约同步生成客户端并验证读写往返；图与内容不一致的响应必须有失败路径用例。
- 按已有工作台设计规范检查实际页面、窄屏、键盘、聚合预览和手动布局；截图不能代替保存、恢复及冲突行为测试。
- 新增异常校验必须有对应非法输入覆盖。相同代码和环境下已有通过结果可以复用，相关改动或新疑点出现后再重跑。
- 实施完成时记录通过、失败和未执行项，按生效内容同步架构说明；不能用本次规格文档检查替代功能验收。

## Out of Scope

- 指令与剪辑画布的 graph 迁移；它们本轮只承接共同保存机制修正。
- 新增领域草稿、独立发布／确认流程、第二套保存系统、每次编辑触发的 graph 投影接口。
- 扩大多覆盖项或跨镜头执行能力、增加批量生成、自动拆分单元、自动采用素材。
- 由 AI 单元组织改写导演创作设计，或通过可见节点与连线重新推断执行范围。
- 通用动态表单、任意载荷协议、反射路径引擎、插件式构建框架及仅为未来可能需求建立的抽象。
- 把图作为第二份持久化业务事实，接收前端节点／边写入，或保留旧前端拼图作为失败回退。
- 在读取时迁移历史身份、批量改写固定记录、恢复旧镜头槽位流程或增加任意历史请求幂等账本。
- 无关业务模块重构、任务中心扩展及现有发布记录修改。
