# 数据库结构清理与 Alembic 初始基线

Status: ready-for-agent

## Problem Statement

维护者初始化空库时，需要重放多轮增删表、数据修补和功能退役操作。最终结构仍包含旧四画布的专属表，应用也仍会识别已无法由现行入口产生的记录。直接把今天的 ORM 固化成初始迁移，会把这些负担一起带入新库。按表名或引用次数批量删除，又可能破坏仍在使用的拍摄、剪辑、并发约束和文件保护。

## Solution

以现行产品能创建、读取和继续使用的数据为起点，核实每项存储的业务用途，先清理结构与历史格式读写，再生成唯一的初始迁移。新库从零开始，只初始化系统设置与内置提示词模板。新建的项目、场次、画布、任务和素材从首次使用开始形成自己的业务历史。实施与验收使用单独新建的 MySQL 测试库。

## User Stories

1. 作为维护者，我希望一次正式迁移即可把空库建到目标结构，以便新环境直接启动 API 和 Worker。
2. 作为维护者，我希望重复执行迁移和种子后仍只有一个初始 head 和一份系统初始数据，以便安全重试部署。
3. 作为系统管理员，我希望新库有可用的全局设置和内置模板，并能自行配置供应商和模型，以便从零开始使用系统。
4. 作为测试负责人，我希望配置缺失或误指当前数据库时测试立即退出，以便在连接或写入当前库之前拦下误操作。
5. 作为项目用户，我希望在新项目中创建章节和场次、保存并重开画布，以便继续编辑刚刚创建的内容。
6. 作为画布用户，我希望为选定的单张模型卡预检并提交生成，以便得到基于本次固定输入的结果。
7. 作为任务用户，我希望查看新任务的状态与产出，以便从任务或画布找到实际生成的文件。
8. 作为用户，我希望重试已成功的保存或提交能取回原回执，以便网络超时时不会重复创建版本或任务。
9. 作为章节编辑者，我希望查看并恢复在新库里保存的章节划分，以便回到一个真实存在的业务版本。
10. 作为资产维护者，我希望角色入库后保留可辨认的来源，图片来源对象只展示实际存在的设定，以便选图与编辑权限仍与来源一致。
11. 作为制作人员，我希望继续使用现行生产计划、批次、拍摄、Take 和剪辑接口，以便旧四画布退役后仍能完成生产流程。
12. 作为文件使用者，我希望正在被任务或作品使用的文件继续受到保护，以便一次删除操作不会破坏已保存的成果。
13. 作为维护者，我希望每个删除候选都能说明其现行读写方和删除后果，以便审查合理冗余以及仍有公开入口的功能。
14. 作为后续开发者，我希望下一次结构变更可以直接接在新初始迁移之后，以便继续使用正式版本管理流程。

## Implementation Decisions

### 删除与保留的判据

对照模型、迁移、数据库约束、API、服务、Worker、前端、运维脚本和嵌入 JSON 的引用，核实拟删除的表、列和兼容分支。记录删除项原先服务的功能，以及需要同步调整的调用方。对看似重复的存储，说明它保护的约束、查询、并发操作或用户可观察行为。数据库结构核对在新建测试库完成。

| 处置 | 对象及理由 |
| --- | --- |
| 旧四画布专属表全部退出 | 版本与复制来源：`directing_scene_versions`、`directing_scene_copy_origins`。单元、指令与执行：`directing_scene_unit_identities`、`directing_instruction_bases`、`directing_scene_video_executions`、`directing_scene_takes`。审查与尾帧：`directing_scene_take_reviews`、`directing_scene_cut_reviews`、`directing_scene_seam_reviews`、`directing_scene_end_frames`。交付与采用：`directing_scene_deliveries`、`directing_scene_delivery_uses`。 |
| 排除历史迁移产物 | 新基线排除三个画布迁移备份表，以及旧 Shot、时间线、旧生成任务和 outbox 等已退役结构。同步移除仅用于旧库转换、回填和恢复的脚本及其入口。 |
| 保留现行生产能力 | 保留生产计划的修订、依赖、批次、拍摄、`directing_takes`、剪辑及其文件引用。仍可提交的 `directing_design` 按现行生产计划处理。 |
| 保留合理冗余 | 保留维持章节当前排序唯一性的计算列、并发消息序号、业务版本与当前指针、提交回执、运行时固定输入、结果集与当前结果指针。任务输入输出、文件使用关系、项目归属及章节使用关系各自保留其实际职责。 |

### 字段与数据格式

- 画布预检逐项核实 `kind` 和 `card_ids`。现行入口只接受单模型，已受理记录中的常量和空列表可退出持久化。保留单卡身份、修订、有效期、依据校验，以及对不支持的执行范围的明确拒绝。
- 角色入库的来源优先使用统一的来源类型和 ID。合并重复列时，覆盖列表筛选、详情、权限和生成输入，现行响应中有用的来源信息可继续派生。
- 图片来源资产允许表达“未提供风格”。清理为满足非空约束而写入的占位风格及读时隐藏逻辑，保留手工创建和编辑资产需要的风格校验。
- 已有公开读写入口、但业务效果待核实的字段单列审查。例如项目默认视频比例仍可在设置页保存，其实际生成效果须沿现行提交路径验证。改变用户可配置能力需要独立的产品决定。
- 移除旧四画布任务领取与终止、专属来源解析、历史结果投影，以及旧导出和交付专属文件引用处理。保留通用任务结果和现行作品的文件保护。
- 清理只能由旧版数据触发的分支，包括旧章节划分回执导入与多套请求摘要、旧画布文档与绑定解析、从旧事件反推运行顺序，以及旧实验消息的输入回退读取。逐一核实现行生产者能写出完整格式，再收敛消费者。保留当前数据的版本冲突、幂等、输入有效性和失效引用校验。公开契约发生变化时同步 OpenAPI、生成客户端及调用页面。

### 建库与种子

清理完成后，用一份固定、无父修订的初始 Alembic revision 替换原有 revision 链。迁移定义显式建表、索引及约束，避免后续 ORM 改动改变初始迁移含义。沿用正式的迁移、系统种子、API 与 Worker 启动顺序。保留未纳管非空库的启动保护。全局模型设置单例在缺失时初始化，重复执行种子保留已配置的默认模型与用户模板。

## Testing Decisions

使用同一个新建的专用 MySQL 测试库，从以下两个已确认的入口验收。验收数据全部由本次测试建立。外部模型调用使用测试替身，任务受理、Worker 执行、持久化和结果读取走现行流程。

1. **正式迁移与种子入口。** 测试启动前校验显式目标配置，在连接前拒绝配置缺失或指向当前库的情况；用配置值即可验证拒绝路径。对专用空库执行正式迁移和种子，再执行一次。核对唯一 head、完整表集合、列、默认值、唯一约束、外键及删除动作、计算列、索引和关键时间精度。逐一断言 12 张退役表和三个画布备份表均缺席。核对初始设置与模板，验证第二次执行可重复且保留用户配置。复用现有隔离 MySQL 的结构反射与并发测试经验，覆盖整个目标结构。
2. **现行 API 与 Worker。** 创建项目、章节和场次，保存、重开画布，为单张模型卡提交任务，经 Worker 处理后读取状态、产出和文件。重放同一请求应返回原结果，冲突请求应被拒绝。用新数据验证划分版本恢复、同章当前排序约束、资产来源与主图、运行结果指向、已引用文件的删除保护。走通生产计划、批次、拍摄和剪辑，验证仍可取得现行 Take。核实现行接口与前端客户端已去除旧四画布专属路径和数据依赖。复用现有画布 API、任务 Worker 和生产计划测试样例。

迁移测试以空库初始化和新基线为起点。移除依赖已删除 revision 或仅验证旧数据转换的用例，为其承载的现行业务行为保留独立覆盖。结构差异和用户可观察行为共同作为验收依据。

## Out of Scope

- 迁移、回填或导入当前库中的配置、业务数据、任务、历史成品及文件引用。
- 对当前数据库做测试、试迁移、版本标记或切换部署。
- 物理删除对象存储中的既有媒体。
- 退役现行生产计划、拍摄、批次、素材使用和剪辑能力，或全面重设计领域模型。

## Further Notes

ADR 0014 记录了旧接口下线时保留历史任务、交付及文件引用的决定。本规格针对从零初始化的新系统，已确认旧四画布整体退出。实施时同步标明该历史保留约定的适用边界，保留原决策背景。评估时的表数和旧 revision 数只描述当时的工作树；验收以审定后的目标结构和实际新库为准。
